### Native export is a distinct, expiring snapshot

The installed Convex CLI requests a server-side ZIP with `POST https://{deployment}.convex.cloud/api/export/request/zip?includeStorage=true`, no request body, using `Authorization: Convex {deploymentKey}`. It waits for `_system/cli/exports:getLatest` and then downloads the ZIP. A metadata-only gate must implement request-and-poll, rather than invoke the full `convex export` command. The query filters `requestor=snapshotExport`; it does not discover dashboard-created `cloudBackup` records. Native completed state is `completed`, not cloud state `complete`. [Native CLI implementation](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/npm-packages/convex/src/cli/lib/convexExport.ts), [export metadata query](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/npm-packages/system-udfs/convex/_system/cli/exports.ts).

Current backend source defaults native export expiration to **14 days from the request transaction** and cleans up expired completed objects. This is source evidence, not a hosted retention service guarantee. The gate must check the returned `expiration_ts`, not hard-code fourteen days. Completed export metadata also contains `start_ts`, `complete_ts` (nanoseconds), `format.include_storage`, `requestor`, and size. Native snapshots are therefore short-lived recovery evidence while unexpired, not durable archival retention. No server-side cross-deployment restore path for native exports was verified; documented native recovery imports a downloaded ZIP. [Export retention model](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/crates/model/src/exports/mod.rs), [export record schema](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/crates/model/src/exports/types.rs), [documented data export](https://docs.convex.dev/database/import-export/export).

Export creation requires `CreateBackups`; status requires `ViewBackups`. Use a **new production deployment-scoped key** with `deployment:backups:create` and `deployment:backups:view` for this gate. Do not reuse an existing production secret or grant delete, import, data-read, or deploy permissions merely to poll metadata. Download permission is separate and would be needed by an explicitly private recovery/archive process. [Create permission enforcement](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/crates/application/src/lib.rs#L1659), [scoped deployment keys](https://docs.convex.dev/dashboard/deployments/deployment-settings), [role actions](https://docs.convex.dev/team-management/role-actions).

The live public management schema explicitly supports this creation contract, authenticated by the authorized saved account and retaining only the newly returned key privately:

```text
POST https://api.convex.dev/v1/deployments/greedy-cardinal-537/create_deploy_key
Content-Type: application/json

{
  "name": "ci-production-backup",
  "allowedActions": [
    "deployment:backups:create",
    "deployment:backups:view"
  ],
  "expiresAt": <epoch milliseconds>
}
```

`expiresAt` must be at least thirty minutes in the future; use an explicit rotation date. `name` is the only required field, and the installed CLI sends only `{name}`. The schema does not document omission semantics for `allowedActions`, so avoid the CLI default and send the explicit two-action array. The follow-up verified the newly created key can query `getLatest` and its live permission metadata contains exactly these two actions. The dashboard permission label for backup viewing still says it is not implemented, although the backend system query currently enforces it. The same first-party UI describes cloud create/restore support for deployment keys as future behavior, reinforcing the observed dashboard authentication limitation. [Live management schema](https://api.convex.dev/v1/openapi.json), [CLI create-key body](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/npm-packages/convex/src/cli/deploymentTokenCreate.ts#L68), [dashboard permission descriptions](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/npm-packages/dashboard/src/components/deploymentSettings/GenerateDeployKeyButton.tsx#L180).

Gate acceptance: assert the expected production deployment; serialize releases; request a new snapshot including storage; poll with a bounded timeout; reject null, failed, old, wrong-requestor, incomplete-storage, or expired metadata; require completion and expiry beyond the release/rollback window **before** the first backend mutation. Keep only sanitized snapshot metadata in CI logs or artifacts. This gate alone does not establish a successful restore or protect data written after its snapshot.

A protected daily refresh can reuse this same request-and-poll contract on the current plan, provided it shares the production release lock and records live expiration proof. Fourteen days is not durable retention or a guaranteed fixed hosted lifetime. Native exports are a separate requestor class from cloud backups; the observed two-cloud-backup entitlement does not establish a two-export cap. Do not claim automatic native retention of two without an explicit, tested cleanup policy and permissions.

For a private native recovery drill, source ZIP access requires only `deployment:backups:download` on the source deployment; use a separate disposable-target key with `deployment:backups:import` and `deployment:backups:view`. The native import protocol uploads ZIP bytes: `POST /api/import/start_upload` returns `uploadToken`; `POST /api/import/upload_part?uploadToken=...&partNumber=1` takes raw bytes and returns a part token; `POST /api/import/finish_upload` takes `{ "import": { "format": "zip", "mode": "requireEmpty" }, "uploadToken": "...", "partTokens": [...] }` and returns `importId`; `POST /api/perform_import` takes `{ "importId": "..." }`. Poll `_system/cli/queryImport` with `{importId}` for terminal state and aggregate `num_rows_written`. The empty-target mode and expected disposable deployment guard are essential. Upload/download tokens must not enter logs. These routes do not accept a source export URL or snapshot ID in place of bytes, so this is a private transfer, not verified server-side cross-deployment native recovery. [Native import handlers](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/crates/local_backend/src/snapshot_import.rs), [import authorization](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/crates/application/src/snapshot_import/mod.rs#L502), [import status authorization](https://github.com/get-convex/convex-backend/blob/deb555a5f50441e5824e3c6ba917dba454d8a277/npm-packages/system-udfs/convex/_system/cli/queryImport.ts).

The first live dependency-review job for PR #47 failed on `path-to-regexp@6.1.0` in the standalone release-tool lockfile: high-severity [GHSA-9wv6-86v2-598j](https://github.com/advisories/GHSA-9wv6-86v2-598j). Both Vercel builders also included the alias `path-to-regexp-updated` resolving to `6.3.0`. The pinned pnpm 10.33.2 audit tree uses the canonical package name as its map key, allowing that alias to overwrite the older version. A local capture of its request for the pre-patch lockfile contained only `6.3.0` and `8.4.2`, while npm's advisory API independently reported the high finding for `6.1.0`. This is an alias collision in the audit payload, rather than an absent installation or a platform-only dependency. [Pinned pnpm audit-tree implementation](https://github.com/pnpm/pnpm/blob/v10.33.2/lockfile/audit/src/lockfileToAuditTree.ts).

The exact same-major override `path-to-regexp@>=6.0.0 <6.3.0: 6.3.0` removes the vulnerable snapshot from the regenerated standalone lockfile. Frozen installation and the existing release audit passed; both installed builders resolved `6.3.0`, matched a normal `/:a-:b` route, and rejected an 80,000-character adverse input inside a two-second subprocess bound. No advisory exception was added. Dependency review remains required because it detected a finding omitted by the pnpm audit payload. CI verification of the corrected PR revision is still required.
