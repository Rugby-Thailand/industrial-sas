## Regression tests (normal suite)

New file: `tests/integration/storage-layout-replay.integration.test.ts`, 5 cases. They use the real `mutationWithOrg` handlers in a `convex-test` tenant world. A snapshot covers buildings, floors, blocks, zones, positions, locations, idempotency records and `storageLayout.*` audit events.

- INV-01, building/floor/floor-count/status: for each mutation, a fresh commit is followed by an exact retry. The retry returns the receipt with `replayed: true` and leaves the snapshot unchanged. The same request ID with changed args returns `REQUEST_ARGUMENT_CONFLICT` without writing. Fresh stale commands still get `VERSION_CONFLICT`, `FLOOR_COUNT_MUST_INCREASE` or `LAYOUT_NOT_EDITABLE`. After the building is archived, a fresh edit is refused, but an exact retry of the earlier update still replays without writing. A cross-org retry is rejected with `TENANT_CONTEXT_DENIED`. After the manage permission is removed, the exact retry returns `ok: false`.
- INV-01, schematic approval: same pattern on an `F1-F2-SB` building with 300 and 150 active zones.
- INV-02: A (x 1000) → B (x 2000) → exact retry of A. The retry returns `replayed: true` and the snapshot is unchanged. The zone and its default position both stay at `Zone B` / 2000. Reusing A's request ID with changed args is a conflict. A fresh update C still syncs the default position, an out-of-floor update is refused, and a cross-org retry is denied.
- INV-06: A floor saved with width 6000 and offsets 2000/1000, then saved with dimensions and offsets omitted, stores no width/depth/offset overrides. Running the layout model on the stored row gives 10000×10000 at 0/0, and it stays valid at 0/0 when the building later grows to 12000×9000. In a second case, an explicit offset 2000 with inherited width is refused as `FLOOR_OUT_OF_BOUNDS` without writing. Omitting only the offset after an offset floor clears it, and the model recenters to 2000. Explicit 0/0 offsets with inherited dimensions are stored as sent.

## Known limitations

- Changed behavior: a reused request ID with changed args now returns `REQUEST_ARGUMENT_CONFLICT` before mutable preconditions, instead of an earlier `VERSION_CONFLICT`. Both are refusals with no write. UI callers clear request IDs after success.
- Replay depends on the target row still existing. A replay whose target row is gone returns `REPLAY_TARGET_MISSING` (unchanged helper behavior). The immutable identity check (`NOT_FOUND` for a missing or other-warehouse building/zone) still runs before replay.
- `updateStoragePosition`, `archiveStoragePosition` and `archiveStorageZone` had the same retry-order root cause. They were closed in follow-up commit `9b140600`; see the follow-up section below.
- INV-06 resolves omitted offsets as "inherit". The current Floor editor always sends explicit offsets, so UI behavior is unchanged.

## Follow-up: same root cause in three more handlers (commit `9b140600`)

This is completeness for the existing INV-01/INV-02 root cause (mutable checks and child writes ran before the idempotency lookup). These are not new ranking IDs. Only `convex/storageLayouts/zones.ts` and the existing replay test file changed.

Change: a local `replayCommittedWrite` helper wraps `replayTenantWriteIfPresent`. Each handler calls it right after its immutable identity and warehouse check (`NOT_FOUND`). The lookup uses the table, operation and `args` fingerprint of the handler's final `updateMasterDataRow`, which commits in the same transaction as the earlier writes. `updateStoragePosition` uses `storageLayout.position.update`, `archiveStoragePosition` uses `storageLayout.position.archive` and `archiveStorageZone` uses `storageLayout.zone.archive`. In `updateStoragePosition`, the `status !== "ACTIVE"` check moved after the replay; it is unchanged for fresh commands. All other fresh checks are unchanged and keep their order.

Every case also covers these points:

- The same request ID with changed args returns `REQUEST_ARGUMENT_CONFLICT` without writing.
- The exact args sent to warehouse `bravoA` are rejected by the wrapper with `WAREHOUSE_OUT_OF_SCOPE`. After a test-only scope grant, the handler's identity check rejects them with `NOT_FOUND`.
- A cross-org retry fails with `TENANT_CONTEXT_DENIED`.

- None of these attempts writes.

Inference, not tested: on baseline, the `updateStoragePosition` retry after archiving would return `NOT_FOUND`, and the occupied `archiveStoragePosition` retry would return `LOCATION_OCCUPIED`. From reading the source: the zone panel keys `archiveZone` request IDs by payload and clears them on success, and `updatePosition`/`archivePosition` have no frontend callers. No UI runtime check was run.

Observation, not changed: `backfillStoragePositions` creates an ACTIVE default position for an INACTIVE (archived) SIMPLE area that has none. This has a different root cause, so it is left for the parent to triage.
