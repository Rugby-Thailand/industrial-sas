## Behavior

- **KIRO-03:** Employee saves retain current and former linked user identities in server-owned `reviewExcludedUserIds`. Review queries and decisions reject those identities. Successful dispositions, certifications, and returns retain their reviewers in `reviewerUserIds`; a reviewer cannot subsequently self-link to that reviewed employee. First legitimate self-link remains supported, including sole-admin setup. Other authorized administrators can continue linking and reassigning accounts. Bounded retained legacy certification/correction history supplements the new reviewer set for reverse-order linkage checks; incomplete history visibly refuses linkage. Already-unlinked pre-deployment employees use the exact tenant-owned `hr.employee.save` audit index and JSON before/after `userId` values to recover former affiliations immediately. The next save persists that complete identity set. Review queues/search share a bounded legacy audit budget; incomplete history refuses review/linkage and marks search incomplete.
- **KIRO-05:** Current periods and review queues apply employment overlap before employee-count limits. Directory selection uses a complete bounded tenant-index collection with an explicit 10,000-row budget; an over-budget read produces the existing visible limit response. Administrative multi-site review shares one scan budget. The 50-person/31-day period limits and queue limits remain enforced. No unbounded reads or silent truncation were added.
- **KIRO-07:** Prefilled correction time sides carry an untouched marker. Unedited sides are omitted from submission, allowing the existing server resolver to retain their exact original seconds/milliseconds. Editing a time or next-day field deliberately produces minute precision, even if the user returns to the displayed original minute. Reviewer disposition forms explicitly retain their previous serialization behavior, including prefilled certified times. Original clock events remain unchanged; server interval ordering and future checks remain authoritative.
- **ROOT-02:** Personal request detail accepts an untrusted string URL segment. Existing tenant storage normalization and ownership checks return the same `NOT_FOUND` result for malformed, absent, wrong-table, foreign-tenant, and other-employee IDs. Registered validators are covered; no `_handler` bypass is used in the new regression tests.

## DAILY-01 integration support

The client agent requested two backend contracts while implementing safe write recovery:

1. `clockIn`/`clockOut` accept optional `expectedBusinessDate`. Fresh execution refuses a different selected business date before creating a day/event. Existing receipt replay occurs before this date check; legacy omitted-date arguments retain their original empty idempotency payload.
2. `hr.recovery.reconcileRequest({ operation, requestId })` returns status only: `COMMITTED` for the actor's own persisted command, or `FENCED` after atomically retiring an absent command. Each operation is whitelisted and checks its existing permission. Durable cancellation rows use an actor-specific reserved operation namespace in the tenant-owned idempotency ledger and never expire. `hrCommand` reads that same fence before any execution/replay, so an original mutation arriving after retirement cannot commit. Another actor/tenant's fence does not retire this actor's command. Recovery does not return receipts, document IDs, navigation ownership, or generic write success.

The additive generated API declaration contains the recovery module import; no cloud deployment or live code generation was performed. `CLOCK_DATE_CHANGED` and `REQUEST_RETIRED` copy belongs to the parallel client change.
