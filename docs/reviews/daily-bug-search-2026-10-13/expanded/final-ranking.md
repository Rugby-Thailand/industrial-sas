## ลำดับการแก้ (waves)

**Wave 1: ความถูกต้องของข้อมูลและ control (6 รายการ)**

- Replay มี 3 root ที่แยกกัน แก้แยกกัน: DAILY-01 ต้องผูก request ID กับ intent และ business date ฝั่ง client INV-01 ต้อง lookup replay ก่อนตรวจ version/status INV-02 ต้องข้าม child sync เมื่อ replayed
- Lost update cluster คือ INV-04 และ INV-03 ทั้งสองแก้ด้วย expected revision และส่งเฉพาะฟิลด์ที่เปลี่ยน แต่เป็นคนละ mutation/ฟอร์ม จึงนับแยกกัน
- KIRO-03 ต้องห้ามแก้ link ของ record ที่ผูกกับตัวเอง หรือให้ reviewBlocker ตรวจประวัติ link

## การรวมและการตัดออก

- **KIRO-08 → ROOT-01:** เป็นหลักฐานสนับสนุนว่าคำตอบ Today เปลี่ยนตามเวลาเพียงอย่างเดียว ไม่ใช่ finding ใหม่ และไม่ได้ยกระดับ ROOT-01 จาก source-demonstrated
- **INV-03 / INV-04:** อยู่ใน cluster lost update เดียวกันและแก้แบบเดียวกัน แต่เป็นคนละ mutation และเวิร์กโฟลว์ (product master data กับขนาดพาเลท) ผลกระทบก็ต่างกัน จึงนับเป็นสองรายการ
- **DAILY-01 / INV-01 / INV-02:** ธีม replay เดียวกันแต่มีสาม root: client ใช้ ID ค้างกับคำสั่งใหม่, server ตรวจ version ก่อน replay และ child sync ไม่ตรวจ replayed
- **KIRO-10 / DAILY-03:** อาการกลับด้านกันในคนละ component จึงนับแยก
- **variant ที่รวมโดยไม่นับเพิ่ม:**
  - INV-01: floor, schematic และ status writes
  - DAILY-01: Save เมนูลัด
  - ROOT-01: หน้าที่อิงเวลาทั้งหมด
  - INV-05: createPallet
  - INV-09: photo/manual
  - KIRO-10: DayScreen/ReviewDetail
  - KIRO-03: การ link กลับด้าน ซึ่งยังไม่ได้ยืนยัน
- **ตัดออก:** tenant/warehouse isolation, repack หน่วยที่ถูกถือ, stack cycle, ขีด `.all(10000)`, กล้อง/decoder, label ledger, barcode ผิดรูป, การย้าย site พนักงาน, DST/ขีด pilot, ข้อกังวล AI ทั่วไป, บั๊กเก่าที่แก้แล้ว และสมมติฐานที่ Kiro ตัดทิ้งเอง
- **รายงานดิบของ Kiro:** [kiro/research.md](kiro/research.md) และ [kiro/findings.json](kiro/findings.json) เก็บไว้เป็นงานวิจัยดิบ ลำดับและ priority ในนั้นเป็นค่าชั่วคราว คำว่า payroll ในรายงานดิบให้อ่านเป็น attendance CSV

## วิธีการและข้อจำกัด

- **การจัดอันดับ:** ดูผลกระทบก่อน แล้วดู reach และเงื่อนไขที่ต้องมี สุดท้ายดูความแข็งของหลักฐาน wave จัดตาม cluster ของแนวแก้ร่วม
- **นิยาม priority:**
  - P0 คือข้อมูลเสีย/รั่วในวงกว้างที่กำลังเกิด ซึ่งไม่มีรายการใด
  - P1 คือข้อมูลเสียหรือสำเร็จปลอมแบบเงียบจากการใช้งานที่ถูกต้อง
  - P2 คือความถูกต้อง, control หรือเวิร์กโฟลว์ล้มอย่างมีนัย
  - P3 คือเงื่อนไขแคบ ผลกระทบเล็ก หรือเป็น UX/ทรัพยากรที่ยังไม่วัดความรุนแรง
