## Five priorities

1. **P1 / Bug F1 — restore the package-assignment path promised by “Scan Packages.”** Storage-unit catalogue CTAs, simple-packing completion, batch Storage actions, legacy-unit links, correction return, and some unit-detail actions route to `/finished-goods/scan`. That route renders `JobScanScreen`, accepts job-ticket identities, rejects `ISAS:` storage QR payloads, and saves only `finishedGoodsJobScans`. It cannot complete the promised assignment of an existing inventory unit. There may be manual measurement/correction alternatives; this finding does not say every unit has no conceivable alternative. Create a dedicated package-assignment route using existing `scanning.resolvePackageCode` and `scanning.confirmScanAssignment`, preserving the job-ticket route separately. Pass selected unit/batch context, define sequence/location confirmation, register the route and owners in the Back inventory, and test completion from the actual caller CTAs. Evidence: `src/features/finishedGoods/unitNextAction.ts:26`; `PackingScreen.tsx:700`; `PackingCompletion.tsx:92`; `BatchManager.tsx:310`; `ProductBatches.tsx:181`; `PalletScreens.tsx:994`; `src/app/[locale]/(desktop)/finished-goods/scan/page.tsx:2`; `jobScan/ticketDraft.ts:12`; `convex/finishedGoods/jobScans.ts:258`; `convex/finishedGoods/scanning.ts:67,291`. Existing `JobScanScreen.test.tsx:620` explicitly verifies rejection of storage QR; `unitNextAction.test.ts:10` verifies the link, not its downstream ability to store inventory.
2. **P1 / Risk F2 — protect unfinished forms consistently.** Stack limit edits use component memory and dirty flags that block reservation, but no draft persistence or dirty navigation guard. Packing's `persist` retains memory when local storage fails and shows a warning; no dirty guard protects that fallback. PhotoCapture's collected photos are not tickets yet, so its parent guard sees zero tickets; closing/toggling intake loses photos. Register the owning drafts, guard only genuinely losable work, retain photo selection while changing input sources, and test header/native Back, cancel→next Back, remount, and failed browser storage. Evidence: `StackScreen.tsx:63,152`; `PackingScreen.tsx:488`; `jobScan/PhotoCapture.tsx:37`; `JobScanScreen.tsx:159,135,471`. Pending server writes are already protected by `useOperation`; the missing protection is unsent local work.
3. **P1 / Improve F3 — make “layout later” a real identity-preserving follow-up.** Add Location creates only `locations.locationType = NAMED_STORAGE`. It is valid for job-ticket mapping and deliberately not geometric storage. Registered catalogue shows “Layout pending / Dimensions and map position not recorded” and only a building link. Neither picker receipt nor catalogue provides a location-specific dimension/completion command. The zone create path generates a new location/code, not conversion of the registered ID. Add an authorized “Complete layout” action keyed by existing locationId, selecting/validating floor and geometry, preserving QR/code and scan references. Offer it after registration and in the registered catalogue; include a truthful “label registered” receipt, not “storage configured.” Evidence: `AddLocationForm.tsx:85,107`; `convex/finishedGoods/jobScanLocations.ts:439`; `src/features/storageLayouts/NamedLocationCatalogue.tsx:82,88`; `convex/storageLayouts/zones.ts:443,472`; `messages/en.json:1533,1555`. Existing wording promises later layout; the absent direct follow-up is a usability gap, not evidence of stock corruption.
4. **P1 / Risk F4 — add conflict protection to product edits.** Product form initializes a complete local snapshot; saves send all product fields without expected version/updatedAt. Backend validates product constraints but unconditionally patches the current row. Two managers editing different fields can overwrite each other's intervening changes. Use expected version, retain draft on conflict, show changed fields, and allow reload/merge with explicit choice. Evidence: `ProductScreen.tsx:211,278`; `convex/finishedGoods/workflow.ts:201,335`. No concurrent production edit was attempted.
5. **P2 / Bug F5 — align ticket intake with server group size.** Manual intake and repeated 20-photo sessions can accumulate >50 tickets; no front-end count cap or blocker appears. Save rejects the entire selection above 50. Display capacity, disable adding beyond 50 across photo/barcode/manual paths, and offer “Save this group, then continue” or safe chunking with a reviewed receipt. Evidence: `JobScanScreen.tsx:207,491,403`; `PhotoCapture.tsx:14`; `convex/finishedGoods/jobScans.ts:38,272`. This is deterministic validation mismatch in source; not reproduced by uploading 51 live tickets.

## API-only capabilities and actual product limits

- `convex/finishedGoods/scanning.ts:67` exports `resolvePackageCode`; `:291` exports `confirmScanAssignment`. Neither has a production frontend call in `src`. `fgRefs` exposes only the scanning location resolver and read-only assignment receipt. The existing assignment endpoint accepts existing unit identities, versions, fullness, top-to-bottom order, sameSize, a real geometric zone/support location identity, and physical acknowledgement; atomically records LOCATION_ONLY placements and marks those units stored. It is the missing package-scan action behind F1. Restoring the UI must retain these checks, not point job-ticket Save at that endpoint.
- `workflow.createPallet` and `workflow.createPacking` still exist and are exposed in `src/lib/convex/finishedGoodsApi.ts:56`; no production frontend component calls them. Current visible unit creation occurs through batch `commitBatch`. These are legacy/API capabilities, not additional visible Create actions omitted from the table.
- `jobScanLocations.create` registers a label-only `locations` row; it cannot reserve physical space. Job-ticket mapping accepts that row. Package `confirmScanAssignment` instead requires zone/support references and a resolved location version. A registered label cannot become either measured placement or an inventory scan assignment simply by reusing its displayed text.
- No visible saved job-ticket field editor or corresponding update endpoint exists; only creation, reassignment and deletion. No direct named-location layout-completion action exists. No batch draft cancellation or historical unit relabel/print command is exposed. These absences are recommendations/product limits; they are not claims that invisible buttons failed at runtime.

## Safety behavior to preserve

- Product creation does not create stock. Packing draft does not create units. Commit is reviewed and atomic. Created batch quantity is conserved; repacks retire old codes and keep revision receipts. Available-subset correction excludes stored, held, moving and supporting units. Backend checks, rather than UI badges alone, enforce these constraints (`BE/batches.ts:242,260`; `BE/batchManagement.ts:41,152`).
- Reservation validates measured geometry, support, recorded occupancy, conditions and measurement freshness. Changing destination preserves the current reservation until successful replacement. Move pickup, completion and return keep source and target held until confirmed; owner and stale source/target checks prevent ambiguous commands (`BE/workflow.ts:1259,1289,1634,1918,2018,2120`).
- Optional QR in moves is a deliberate supported acknowledgement path, not a bypass to report as a defect. Ordinary reservation storage still requires destination verification. Hardware scanning validates identity, not the exact physical coordinates; prompts correctly ask operators to place the unit according to the guided position (`BE/workflow.ts:1939,2042`; `FG/PalletScreens.tsx:1275`).
- Request identities, pending guards and live operation completion owners already prevent duplicate submissions and departure during writes. Packing additionally freezes uncertain commands in local recovery storage. ## First-time and operator efficiency

A first-time operator can infer product→batch preparation from the catalogue empty state and product copy. Their hardest decision is whether they are scanning a job ticket, assigning an already-created package, or configuring a measured position. The currently overlapping “Scan Packages,” “Scan pallet,” job-ticket record, named label and LOCATION_ONLY vocabulary makes these tasks easy to confuse. F1 and F3 should be solved before adding more explanatory text. Use visible task-specific actions: “Record job tickets,” “Assign these package labels,” “Plan exact storage,” and “Complete this location's layout.”

A frequent operator benefits from retained filters, shared scanners, manual handheld-code entry, group fullness, quantity splitting, copy dimensions and immutable operation receipts. Recoverable friction is repeated geometric checking after correction, erased measurements after subset split, new labels after a repack without a relabel receipt, and immediate bulk remapping when clicking a destination. The solutions above keep these steps efficient while preserving physical truth; do not add routine confirmations to every low-impact action.

For a distracted phone user, sticky ticket/packing/move actions and labelled manual fallback are useful. The remaining source-supported loss risks are photos collected before sending, unsaved stack limits, failed packing storage, and memory-only ticket recovery after refresh. Actual touch target sizes, camera behavior, focus timing and native Back on the relevant real devices remain unverified.
