# คลังและ Storage Layout — Action audit

ตรวจโดย GPT-6.1-Sol ตามที่ผู้ใช้ระบุ แยกอ่านงานออกแบบ/ตั้งค่าผัง งานสินค้า/จัดเก็บ และหลักฐานจาก browser/detector อย่างอิสระ แล้วผู้ประสานงานตรวจข้อค้นพบสำคัญกับโค้ดอีกครั้ง

ขอบเขต: คลังและ Storage Layout รวมหน้าที่เชื่อมกับ Finished Goods ไม่รวม HR ตรวจ current working tree ทั้งหน้าสร้าง ตั้งค่า แก้ไข รายละเอียด dialog และกฎบันทึกฝั่งเซิร์ฟเวอร์ หน้าเว็บ production ใช้ยืนยันพฤติกรรมบางกรณีเท่านั้น เพราะหน้าที่ deploy อยู่ต่างจาก working tree บางส่วน ไม่มีการส่งคำสั่งแก้ข้อมูลจริง

ครอบคลุม route ของ Storage Layout 6 หน้า, Finished Goods 12 หน้า และหน้า setup ที่เกี่ยวข้อง รวม 19 route patterns ไม่แยกซ้ำตามภาษา ตารางละเอียดมี **60 กลุ่ม action ฝั่งผัง + 189 กลุ่ม action ฝั่งสินค้า/คลัง** รวม read-only, recovery, action ที่ยังขาด และ API-only capabilities บางแถวเชื่อมข้ามโมดูลจึงไม่ใช่จำนวนปุ่มที่ไม่ซ้ำกัน 249 ปุ่ม ตารางสรุปด้านล่างรวมเป็น **28 กลุ่มสิ่งที่ควรแก้**

ไฟล์ตาราง: [28 กลุ่มสิ่งที่ควรแก้ — CSV ภาษาไทย](findings.csv) · [Action inventory ทั้งสองส่วน — 249 แถว CSV](actions.csv) ใช้ UTF-8 พร้อม BOM เพื่อเปิดข้อความไทยใน Excel

**ข้อสรุป:** แนวคิดอาคาร → ชั้น → จุดจัดเก็บ และกฎจอง/ย้ายมีเหตุผลรองรับ แต่ action บางตัวพาไปคนละงาน บางฟอร์มแก้ข้อมูลเดิมไม่ได้ และรายละเอียดของการบันทึก/ยกเลิกยังไม่สม่ำเสมอ ควรแก้ความถูกต้องของ flow พร้อมกับจัดหน้าจอตามงาน

## วิธีอ่าน

- **P1:** งานหลักติดขัด เสี่ยงสูญเสียข้อมูล หรือไม่สามารถฟื้นตัวจากข้อผิดพลาดได้ชัดเจน
- **P2:** ลำดับงาน/ความหมายชวนเข้าใจผิด หรือทำให้ต้องอ้อมหลายขั้น
- **P3:** เพิ่มประสิทธิภาพและความสม่ำเสมอ
- **หน้าเว็บ:** ตรวจพฤติกรรมจริงผ่าน T3 แบบไม่บันทึกข้อมูล
- **โค้ด:** ยืนยัน call chain/เงื่อนไขจาก source และอ่าน test ที่เกี่ยวข้อง ยังไม่เท่ากับทดสอบทุก state ใน production
- **ข้อเสนอ:** การตัดสินใจด้านผลิตภัณฑ์ ไม่ใช่การกล่าวหาว่า logic ปัจจุบันผิดทั้งหมด

## Action ที่มีเหตุผลและควรเก็บไว้

- แยกสร้างสินค้า, เตรียม batch และสร้างหน่วย stock ออกจากกัน; การแบ่งจำนวนต้องรวมได้เท่าเดิม และการ repack เก็บประวัติ
- การจองตรวจขนาด/ตำแหน่ง/เงื่อนไขจริง; การย้ายคงสิทธิ์ที่ต้นทางและปลายทางตามสถานะจนยืนยัน ไม่ควรลดขั้นตอนจนข้อมูลไม่ตรงของจริง
- เลือกดูตำแหน่งใน map/list โดยไม่เขียนข้อมูล; มี shared Dialog/Sheet, workflow Back, dirty/pending guard และ completion owner อยู่แล้ว ต้องแก้ caller ที่หลุดเป็นรายกรณี
- แยก “บันทึกใบงาน/ลงทะเบียนชื่อ” ออกจาก “ยืนยันจัดเก็บสินค้า” และแสดงสินค้าที่ยังไม่วัดขนาดตามความจริง
- request identity, retry, occupancy checks และ server permissions เป็นกลไกที่ควรคงไว้; การเพิ่ม feedback หรือทำหน้าจอง่ายขึ้นไม่ควรข้ามกฎเหล่านี้

## รายละเอียดทุก action และหลักฐาน

- [Storage Layout — 60 action families](layout-actions.md): รวม action ที่ดีอยู่แล้ว ช่องว่าง UI, lifecycle, setup และ administrative API โดยแยกจาก action ที่ผู้ใช้กดได้จริง
- [Finished Goods / inventory — 189 action families](inventory-actions.md): สินค้า, batch, packing, measure, placement, reserve/release, move, stack, scanner, photos/AI และ scanned records
- [หลักฐาน browser และ detector](evidence.md), [ผัง PD ที่จับภาพรอบนี้](pd-storage-map.png), [การตรวจข้ามหน้า](cross-surface-checks.md)

คำแนะนำ F20 ถูกจัด P2 ในตารางรวมเพราะการลงทะเบียนใบงานปัจจุบันทำงานตามขอบเขตที่ระบุได้อยู่แล้ว แต่ follow-up “ทำผังภายหลัง” ยังไม่ครบ รายงาน inventory ให้น้ำหนัก P1 ด้านการจบ workflow; ไม่มีหลักฐานว่าช่องว่างนี้ทำ stock เสียหาย

## ลำดับลงมือที่แนะนำ

1. แก้ flow ที่ชี้ผิดงานและช่องโหว่การบันทึก: scanner, precision, error feedback, warehouse/draft guard, product conflict และ preservation of block metadata
2. เชื่อมการสร้าง/ตั้งค่าให้จบงานได้: ตำแหน่งที่ลงทะเบียนแล้ว → ผังจริง, การจัดการชั้น/จุด/แร็ก, lifecycle ของแบบร่างและเปิดใช้งาน
3. จัดหน้าจอตามงาน: ค้นหาและดูของ / จัดเก็บและย้าย / แก้ไขผัง โดยเก็บ selection และบริบทเดิมไว้ตลอด

## เกณฑ์ตรวจหลังแก้

- สร้างสินค้าหรือหน่วยจัดเก็บแล้ว action ถัดไปทำงานที่ข้อความบนปุ่มสัญญาไว้ และอ้างอิงหน่วยเดิม
- เปลี่ยนเฉพาะชื่อหรือสีต้องไม่เปลี่ยน geometry/metadata ที่ผู้ใช้ไม่ได้แก้ และขนาดเดิมจากผังต้องบันทึกกลับได้ครบความละเอียด
- network failure ต้องแสดงผลชัดเจน เก็บ draft และ retry ได้โดยไม่สร้างรายการซ้ำ
- แต่ละ form ระบุว่า action ใดบันทึกทันที และ action ใดเป็นเพียงการแก้ draft รอบนอก
- header/native Back, Close/Cancel แล้ว Back ครั้งถัดไป, direct link, locale/query/hash, dirty/pending, nested foreground, completion, Forward และ refresh/remount ต้องมี caller-level evidence ตาม [Back contract](../../contracts/back-navigation.md)
- เมื่อเปลี่ยน navigation จริง ให้อัปเดต inventory ด้วยเหตุผลเฉพาะ action และรัน `pnpm check:navigation`, ESLint และ caller tests ที่เกี่ยวข้อง การ audit นี้ยังไม่ได้แก้ production navigation จึงไม่ได้อ้างว่าผ่าน gate จากการเปลี่ยนแปลง

## ขอบเขตหลักฐาน

ไม่มีการแก้ production code หรือข้อมูลจริงในงานนี้ การอ่าน test ยืนยันเจตนา/เงื่อนไขของ test แต่ไม่ได้เท่ากับรัน test ใหม่ทุกไฟล์ งานย้ายและจัดเก็บที่ต้องมี stock/reservation ตรวจจาก source เป็นหลักเพราะคลัง production ที่เปิดไม่แสดงรายการสินค้าสำหรับทดลองแบบครบวงจร

Assessment A ถูกสรุปก่อนผู้ประสานงานอ่าน detector เพื่อไม่ให้ style warnings ชี้นำข้อค้นพบ ฝั่ง production source scan 157 ไฟล์ไม่พบ detector warnings; นั่นไม่ใช่ผลรับรอง flow, accessibility หรือ navigation ข้อความเตือนเรื่องฟอนต์ใน prototype และ overlay ที่บังตัวเองไม่ถูกใช้เป็นข้อบกพร่องของระบบจริง รอบนี้ screenshot ทำงานได้แล้ว ไม่มี audit live-server หรือ injection ค้างอยู่ มีเพียงไฟล์หลักฐานที่เก็บไว้
