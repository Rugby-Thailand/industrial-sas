# Storage Layout action assessment A — 2026-10-13

Independent GPT-6.1-Sol assessment of the **current production warehouse / Storage Layout module**, not the earlier prototype. Read-only audit; only this report was written. Existing dirty working-tree changes were preserved. Baseline HEAD: `733c6acad348f1c024ef033f9d6ae8300e45e363`; the working files, including uncommitted changes, are the source of truth for source findings. No other assessment or detector output was read before completing this assessment.

The basic workflow makes sense: select the warehouse, create a draft building, define floor geometry and unavailable areas, add QR-addressable spots, then activate it. The implementation has substantial safety and navigation infrastructure. Its weakest points are precise measurement editing, preservation of imported area metadata, failure recovery, and ambiguity about whether an action affects one spot, an entire building, or an unsaved floor draft.

## What is already strong

1. **Server safety is real.** Tenant/warehouse permissions, geometry bounds and overlap validation, stock/reservation/move checks, stable QR identities, idempotent request keys, and expected building/floor versions protect writes. `tests/integration/storage-occupancy.integration.test.ts:474` deliberately checks occupied changes even when override flags are supplied. Safe occupied envelope widening and color-only exceptions are also tested.
2. **Back and draft ownership are deliberately implemented.** Named workflow steps, shared Dialog/Sheet, draft scopes, child registries and live completion ownership exist. Tests cover native settings/impact Back, retained dirty floors, mobile inspector closure, and pending building creation (`StorageLayoutScreens.test.tsx:2498`, `:2563`, `:2628`, `:2675`, `:2717`, `:2783`). Preserve these while fixing specific caller gaps.
3. **Inspection reflects operational reality.** Measured/unmeasured stock, reserved/stored/moving units, QR deduplication, appropriate View/Move/Continue links, live inventory subscriptions, and shared map/table selection are implemented. The demo is explicitly isolated from writes. No proposal should replace these strengths with static generic cards.

## Persona friction and cognitive load

| Persona                       | Main friction                                                                                                                                                                                                                                                 | Design consequence / solution                                                                                                                                                                                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First-time warehouse operator | A plus labeled “Add storage stack” creates an area + implicit leaf, while registered labels without geometry are created elsewhere. “Reserved zone” can mean blocked floor area or reserved goods. A full PD plan starts a new 2 m square in an invalid spot. | Start with a short decision: inspect existing spot, register a label, or plan a measured spot. Use one domain vocabulary and explicit persistence scope. When no fit exists, explain it before presenting a failed default. Keep camera operations secondary to Find, Inspect and the permitted task. |
| Experienced warehouse manager | Precise measurements are rejected; imported obstacle metadata can disappear; no UI for rack leaves or lifecycle recovery; zone updates can overwrite stale drafts. Repeated building-status switches and disabled confirmations make scope hard to scan.      | Preserve survey precision and hidden metadata; expose area/position hierarchy and safe scoped management. Use preflight summaries for publication/archive, conflict-aware drafts, batch labels and Undo for local changes. Show operation scope/count before durable commands.                        |

Intrinsic load is justified: floor geometry, obstacles, exact addresses and occupancy are related but distinct. Extraneous load comes from inconsistent nouns, hidden two-stage persistence, several independent view switches, ambiguous total count and action scope, and nonexistent affordances for backend-supported models. Reduce that load with precise task names and progressive disclosure, while keeping live occupancy and safety rules visible. Do not merge all edit surfaces into one global Save: floor drafts and immediate zone commands have different transaction boundaries and must remain explicit.

## Follow-up verification required

Before accepting fixes, exercise legitimate fractional survey values; typed obstacle label/color save and reload; thrown response and uncertain-outcome retry in each writer; independent dirty settings forms; viewer/permission-revocation behavior; total-floor semantics; and concurrent zone edits. For navigation changes follow `docs/contracts/back-navigation.md` and the reviewed inventory, including explicit Close/Cancel → next Back, direct links, locale/query/hash, pending/dirty drafts, nested foregrounds, completion, Forward and remount. Static inventory compliance does not replace those caller cases. This assessment makes no claim that these unexercised runtime cases already fail or pass.
