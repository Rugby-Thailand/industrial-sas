The shared hook adds `cancelFocusTarget(opener)` and owns its use in the dialog close lifecycle. When the option is omitted, it passes no additional focus handlers, preserving existing storage behavior. When present, it records the opener, asks for a target only on cancellation, and suppresses return focus after an accepted transition. History buffering, guard chaining, pending writes, save failure handling, locales and draft discard behavior are unchanged.

The HR provider remembers the actual focused control in its existing `<main>` region only while an HR draft or pending write is registered. It records pathname and search so a previous page's focus is stale. A normal connected, usable opener retains the ordinary dialog return. Otherwise, the provider uses the remembered control only while it is still usable in the same retained region. Disconnected, transient popup, hidden, inert, aria-hidden, disabled and disabled-fieldset targets are rejected, including computed hidden visibility and display-none ancestors. If the control becomes unusable, the already focusable retained main landmark is the fallback. No new HR DOM, first-control query or arbitrary target is introduced.

`useHrWrite` and its independent tests still match their post-rebase snapshots. Production callers use `submit` and `retry`; an uncertain write retains the pinned command and request ID. Organization/actor scoping prevents account crossover. `reset` is used only after SAVED in the current Settings caller. Theoretical misuse of the exported low-level API and reload recovery limits did not justify changing current behavior. Server authorization and argument fingerprinting remain authoritative. SearchDialog's accepted-navigation focus handling, permission checks and context isolation were preserved.
