# Convex official cost and performance baseline

Verified 2026-10-13 against primary Convex documentation. Repository dependency: `convex@1.46.0`. This is a research baseline, not a production usage measurement. No production calls, configuration changes, or application edits were made.

## What the supplied screenshot establishes

The reported September 29–October 29 window shows 171K calls, 0.0031 GB-hours compute, 12.21 MB database storage, database I/O of 1 GB included plus 641.01 MB on-demand, and 24.05 MB egress. The Function Calls breakdown reportedly ranks `buildingStatusControl` at 40K and `readCurrent` at 34K. These are supplied observations, not independently retrieved dashboard data.

Database I/O measures cumulative database reads **and writes**; storage measures the retained dataset; egress measures delivered bytes; calls count invocations; compute is measured in GB-hours. Consequently a small retained database can accumulate much larger I/O through repeated reads. [Usage metrics](https://docs.convex.dev/production/usage-limits)

Calls ranking cannot establish I/O ranking. A frequently called cached query can have negligible database reads; a less frequent uncached geometry scan can dominate reads. Explicit client calls, subscription updates, scheduled executions and file accesses count as calls. Cache hits eliminate database bandwidth, not every other billing dimension. [Function limits and accounting](https://docs.convex.dev/production/state/limits), [Realtime caching](https://docs.convex.dev/realtime)

Current public Starter pricing lists 1 GB included I/O and $0.22 per additional GB; Professional lists 50 GB and $0.20 per additional GB. **Illustration only:** 641.01 MB at $0.22/decimal GB is approximately $0.14 in a US region; with a 1.3× regional multiplier it would be approximately $0.18. This is not the account's invoice or verified rate. Exact plan, billing units/rounding, taxes, other charges, and screenshot timing are unverified. Exceeding an allowance alone does not imply a large dollar bill. [Official pricing](https://www.convex.dev/pricing)

## Comparison checklist

| Area                     | Official baseline                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Audit question for this repository                                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query dependencies       | Results are automatically cached and invalidated when underlying data changes; a query's reads share a consistent snapshot. [Queries](https://docs.convex.dev/functions/query-functions)                                                                                                                                                                                                                                                                             | Does frequently changing inventory invalidate a query that also reads large static layout documents? Is the September split still used by all clients?                                                                      |
| Clock dependencies       | Avoid query `Date.now()`; it can stale time-dependent answers and frequently invalidate caching. Prefer scheduled state changes or coarse explicit time arguments where appropriate. Time passing alone does not proactively rerun subscriptions; cache expiration and subscription reruns are different events. The pages reviewed do not establish a universal numeric expiration interval. [Best practices](https://docs.convex.dev/understanding/best-practices) | Trace helpers, authorization and request ID creation, not just query handlers. Preserve expiry and step-up correctness when removing clock reads.                                                                           |
| Auth caching             | Query context is part of determinism. Auth identity fields vary with JWT claims; Convex excludes time-varying Clerk `fva` because it would break caching. [Auth functions](https://docs.convex.dev/auth/functions-auth)                                                                                                                                                                                                                                              | Measure cache reuse per identity and arguments. Do not assume tenant peers share one cache entry just because query arguments match. Never remove auth checks to improve cache hits.                                        |
| Index range              | Equality constraints must follow the leading index fields, then optional bounds on the next field. `.filter()` does not narrow scanned rows. An index without a range can scan the whole table. [Indexes](https://docs.convex.dev/database/reading-data/indexes/)                                                                                                                                                                                                    | Is filtering by organization, building, status or pallet done inside the range? An indexed query is not necessarily selective. Check index order before removing a prefix index; longer indexes can change result ordering. |
| Bounded reads            | `.collect()` should be restricted to predictably small result sets. Roughly 1000+ potential documents merit narrower ranges, pagination or changed data models. Broad scans also expand invalidation/conflict dependencies. [Best practices](https://docs.convex.dev/understanding/best-practices)                                                                                                                                                                   | Record cardinality assumptions and worst-case growth per tenant. A present-day small table does not prove a lifetime bound. Avoid arbitrary `.take()` truncation when complete results are required.                        |
| Pagination               | Cursor pages are reactive and may grow/shrink as records change. [Pagination](https://docs.convex.dev/database/pagination)                                                                                                                                                                                                                                                                                                                                           | Are accumulated history pages still subscribed after loading more? Does a list need all old pages live? Retention is a client-lifecycle choice, not a free cost guarantee.                                                  |
| Page scan bound          | `maximumBytesRead` and `maximumRowsRead` can limit paginated scans; `numItems` alone may not bound rare-item filtering. Nested query/mutation calls share transaction limits. [Writing data](https://docs.convex.dev/database/writing-data)                                                                                                                                                                                                                          | Check installed 1.46.0 typings before adopting newly documented controls. How much do tenant filters scan to return one page?                                                                                               |
| Document shape           | `getDocumentSize` includes system fields; `getConvexSize` measures Convex encoding rather than JSON string length. [Types](https://docs.convex.dev/database/types), [Values API](https://docs.convex.dev/api/modules/values)                                                                                                                                                                                                                                         | Is a large geometry/object document fetched to produce only a count or status? Reducing the returned object alone does not undo database reads. Measure document reads, not response size.                                  |
| Counters/summaries       | Denormalized counts can replace repeated collection scans; redundant indexes add storage and write overhead. [Best practices](https://docs.convex.dev/understanding/best-practices)                                                                                                                                                                                                                                                                                  | Would per-building/per-floor summaries materially reduce measured read I/O? Require atomic updates, delete/move coverage and reconciliation. A central counter may introduce a hot write dependency.                        |
| OCC                      | Transactions validate their read sets and retry on conflicts; mutations are atomic and serializable. [OCC](https://docs.convex.dev/database/advanced/occ)                                                                                                                                                                                                                                                                                                            | Measure retry counts before claiming counter contention. Large read sets and shared summary records can cause work to repeat.                                                                                               |
| Parallel joins           | `Promise.all` fetches independent joins concurrently. [Reading data](https://docs.convex.dev/database/reading-data)                                                                                                                                                                                                                                                                                                                                                  | Distinguish latency improvements from byte savings. Parallelizing the same reads does not remove them; memoize repeated IDs within an execution where applicable.                                                           |
| Actions and helper calls | Actions lack query caching. Plain helpers reduce unnecessary `runAction` overhead. [Other recommendations](https://docs.convex.dev/understanding/best-practices/other-recommendations)                                                                                                                                                                                                                                                                               | Does fan-out create separate execution/call overhead? Parallel `runQuery` calls from an action still use distinct transactions, not one shared snapshot. Group related reads when consistency requires it.                  |
| Background workloads     | Cron jobs invoke internal queries/mutations/actions on schedules. [Cron jobs](https://docs.convex.dev/scheduling/cron-jobs)                                                                                                                                                                                                                                                                                                                                          | Attribute recurring scans and cleanup to schedules, including when users are absent. Bound work and avoid writing unchanged state that invalidates live queries.                                                            |
| Client lifecycle         | Passing `"skip"` to `useQuery` prevents backend communication; one-off queries are available for callback reads. [React](https://docs.convex.dev/client/react/overview)                                                                                                                                                                                                                                                                                              | Are closed dialogs, inactive tabs and hidden panels still mounted with active arguments? Preserve subscriptions where live data is product-critical.                                                                        |

Installed client evidence: `node_modules/convex/src/react/use_paginated_query.ts:273` calls `useQueries(currState.queries)`; `loadMore` adds the next query around line 420 rather than simply discarding previous pages. Therefore accumulated pages should be reviewed as reactive subscriptions. This is installed-source evidence, not a claim that every pagination implementation retains all pages forever.

## Measurement methodology

1. Fix the exact team/project, deployment type, time window and metric. Separate production, preview, development, legacy clients and background jobs. Capture **database I/O** function breakdown independently of Function Calls.
2. For each candidate, capture cold and cached executions, arguments, identity category, document count, read/write bytes, return bytes, run reason, cache hit rate and tail latency. Dashboard function charts expose invocations, cache hit rate, errors and execution percentiles. [Function dashboard](https://docs.convex.dev/dashboard/deployments/functions)
3. Production log streams expose `database_io_read_bytes` plus `database_io_write_bytes`; their sum is function I/O. Other fields include document counts, written index rows, `function.cached`, execution time, `run_reason`, scheduler attribution and OCC retries. Group by deployment and function; sum actual byte counters instead of multiplying a calls chart by a guessed document size. Log streams currently require Pro. [Log schema](https://docs.convex.dev/production/integrations/log-streams)
4. Use returned `usageStats` where the existing execution tool exposes it, keeping raw fields and versions. That name is the repository's historical measurement evidence, not a promised portable public billing API. Current official attribution documentation recommends log stream resource fields. Do not assume a tool's field names match current log schemas. [Tracking usage](https://docs.convex.dev/platform-apis/track-usage)
5. Inspect index write amplification separately: each document write produces index entries, including built-in indexes, and indexed-field changes also remove stale entries. Do not infer an exact billing-byte formula from row counts. [Log schema](https://docs.convex.dev/production/integrations/log-streams)
6. Compare equivalent traffic and data cardinalities after a change. Report both absolute and per-operation I/O, cache hits, calls and latency; include cold-load behavior. Local JSON byte estimates and fixtures establish regressions, not realized invoice savings. Health insights identify recent OCC and resource-limit problems. [Insights CLI](https://docs.convex.dev/cli/reference/insights)

## Prioritized structural audit questions

1. **Measurement first:** which functions dominate actual read/write I/O in the current window? Are 40K/34K call leaders cache hits, data-change reruns, initial subscriptions or identity changes?
2. **Check the existing fix remains effective:** `docs/plans/convex-database-io-optimization.md` records September's 3.45 GB `getStorageBuilding` attribution and measured PD/FG1 uncached reads. These are historical facts from a local note, not current baseline. Confirm layout/inventory isolation and absence of legacy whole-building subscribers before redoing the optimization.
3. **Inspect shared auth/read dependencies:** `convex/lib/tenantFunctions.ts:324` already uses membership creation time only under restrictive time-independent conditions. Audit remaining query helper clocks and frequently updated permission/organization documents. `convex/workspace/current.ts:63` reads warehouse/navigation information; high calls alone do not prove expensive reads.
4. **Inspect status summaries:** `convex/storageLayouts/catalogue.ts:650` exposes `buildingStatusControl`. Compare its actual read set with the UI fields it returns, and evaluate a lightweight summary only after measuring uncached I/O/invalidation.
5. **Inspect large lists, joins and job scans:** prove selectivity and bounds, deduplicate repeated IDs, then evaluate pagination or summaries with correctness tests. Avoid prioritizing cosmetic Promise parallelism as a cost fix.
6. **Inspect subscription ownership:** audit route shells, inactive panels and accumulated paginated histories. Skip/unmount only when product behavior permits it.

`Date.now()` is frozen at function-start time within an execution, and globally at deploy time outside functions. This deterministic runtime behavior does not create a subscription timer. [Runtimes](https://docs.convex.dev/functions/runtimes)

## Uncertainty boundaries

This research did not establish the exact authenticated cache-key implementation, cache lifetime, Date.now invalidation schedule, per-index billing-byte formula, account plan, screenshot rate, current per-function I/O, or realized savings. Treat cross-user sharing, invoice estimates and reduction percentages as unverified until deployment/account evidence answers them. Query cache hits are explicitly documented as free of database bandwidth; that is narrower than saying cached queries are entirely free.
