# Storage-layout and finished-goods cost/performance audit

Date: 2026-10-13. Research only; no source, environment or deployment changes. Reviewed the current dirty working tree, AGENTS.md, the September I/O optimization and catalogue-query plans, and the October 10 backend warehouse review. Findings below were independently checked against current source. No production metrics, data distribution, test executions or billing savings were measured. References use current line numbers, which may move with concurrent work.

## Dashboard interpretation

The supplied Sep 29–Oct 29 panel reports 171K function calls, 1 GB included database I/O plus 641.01 MB on demand, and 12.21 MB database storage. `buildingStatusControl` has approximately 40K calls and `workspace/current.readCurrent` 34K. This is a call ranking, **not database-I/O attribution**. Neither small stored size nor high call count identifies the dominant byte reader. Repeated reads of the same small dataset can explain I/O exceeding storage.

`buildingStatusControl` itself reads one building and, only for ACTIVE buildings, at most two indexed presence checks (`convex/storageLayouts/catalogue.ts:650–670`, `:32–52`). Those checks use `first()`, not a full placement scan. Its authorization wrapper adds shared overhead, covered by the other audit. Obtain per-function execution usage/cache-hit statistics before claiming this function dominates the overage. The historical September 323,099-byte/436-document PD cold read is genuine execution evidence from the plan, but predates the layout/inventory split and does not establish October's attribution.

## Ranked remaining issues

### 1. Warehouse-wide readiness generation invalidates unrelated catalogues and forces repeated totals work (P1)

Evidence: `convex/lib/finishedGoodsSummary.ts:223–298` tracks pallets, products, moves, buildings, floors, zones and positions. Every touched warehouse's flush increments the same readiness document's `generation`. Storage building pages read it at `convex/storageLayouts/catalogue.ts:413–416`; location pages at `convex/storageLayouts/locationCatalogue.ts:328–330`; FG pages/summary at `convex/finishedGoods/catalogue.ts:338,369,378,414,497,517`. Batches also read readiness at `convex/finishedGoods/batches.ts:472,519`. This remains unfixed from October 10.

A pallet write can therefore rerun the building list's query despite changing no building row. The metadata document is also a common read/modify/write conflict surface for concurrent warehouse mutations. In-progress `paginatedScan` state is discarded when generation differs (`convex/lib/cataloguePagination.ts:117–128`); this is a restart of accumulated work, not necessarily an explicit `reset` response. Sorted FG scope incorporates generation, so old sorted cursors can reset. Do not generalize that every unsorted completed page resets.

Warehouse totals remain a complete product scan, bounded to 100 products **per invocation**, not constant-cost totals (`convex/finishedGoods/catalogue.ts:490–590`). Each product's `readProductSummary` rereads readiness and reads its summary (`convex/lib/finishedGoodsSummary.ts:148–153`). The mounted catalogue advances this scan reactively (`src/features/finishedGoods/FinishedGoodsCatalogue.tsx:112–137`). For a hypothetical 1,000-product warehouse, a full pass requires at least ten chunks, product documents plus 1,000 summary lookups plus 1,000 readiness lookups; authorization and native range splitting add overhead. A generation change can discard accumulated signed-cursor totals and start the pass over. This example is structural, not the known production product count.

Remedy: separate backfill readiness/version/key from change signals; separate storage and FG signals and read them only where frozen cursor state actually needs them. Cache readiness once per query and pass its verdict into summary hydration. Maintain exact warehouse totals transactionally from contribution deltas, including product count and unit-name reference counts so product deletion/unit changes preserve current output. A small totals row makes reads cheap but introduces a hot write document; measure OCC retries before choosing one warehouse row versus sharded counters. New projections need resumable backfill and explicit unavailable state until complete. Keep authenticated subscriptions and row revalidation.

Verify: instrument docs/bytes/ranges and update frames on building, location and FG catalogues during 20 pallet writes; assert storage metadata reads do not rerun for FG-only changes. Test sorted/unsorted cursor contracts, sparse scans under continuous writes, exact totals after moves, retirements, replacements, deletes and unit changes. Compare production cache misses and OCC retry logs before/after. Fixing readiness alone reduces unnecessary invalidation but does not remove the totals scan.

### 2. Recommendations repeatedly load every zone context, mostly in sequence (P1 performance/capacity; savings require usage)

`convex/finishedGoods/workflow.ts:930–973` loads all warehouse zones and awaits `locationContext` for each. `:537–615` rereads zone, building, floor and location, positions, all floor blocks and the two placement statuses. Later loops read position locations and stored supporting pallets (`:638–744`), and recommendations validate each supporting pallet. Live callsites are `src/features/finishedGoods/PalletScreens.tsx:586–594` and `MoveScreen.tsx:157`.

For each accepted active zone there are eight base DB ranges before position/support joins: four gets and four indexed reads. Shared floor blocks/parents are fetched repeatedly. Draft/inactive parents are rejected after partial context reads, rather than excluded in initial enumeration. Every relevant placement mutation can invalidate a broad warehouse read set. Serial awaits amplify latency even where bytes are modest. With a hypothetical 200 active zones, the baseline is 1,600 ranges before joins/auth; the 4,096-range limit is a plausible future constraint, not a demonstrated production failure. Zone count alone is insufficient to predict it: positions and stored pallets determine additional reads.

Remedy: use query-local promise memoization for buildings, floors, locations, pallets/products and per-floor block queries; pass the already loaded zone into a shared context loader. Enumerate ACTIVE buildings and their ACTIVE zones with existing indexes when equivalent. Keep preview and reservation using the same domain checks. Parallelize independent reads with bounded concurrency rather than serializing unrelated work or unbounded `Promise.all`. Filtering by storage condition earlier changes diagnostic precedence when an unmeasured zone also mismatches; preserve behavior or explicitly decide that tradeoff.

Verify: old/new deep parity for SIMPLE/RACK/PLATFORM, inactive parents/locations, source/target move holds, unmeasured packages, stacking and error reasons. Count ranges, bytes and maximum concurrent calls at realistic imported layouts and increasing inventory. Measure time to first destination and per-execution database usage, separately from frontend rendering.

### 3. Building catalogue opens separate row subscriptions for occupancy and controls (P2; directly relevant to 40K-call panel)

Current UI: `src/features/storageLayouts/StorageLayoutScreens.tsx:245–279,304–307` mounts a status toggle and occupancy cell for each visible building. `BuildingStatusToggle.tsx:57–60` opens statusControl **only when the user may activate and the building is not archived**. Thus a page of B rows opens B occupancy queries and between 0 and B control queries, plus its page query; calling it universally 2B would overstate actual usage. Repeated subscribers with identical authorized arguments can share Convex cache work, so subscription count is not automatically unique backend execution count.

`buildingOccupancy` reads one building and every RESERVED/STORED placement within it (`convex/storageLayouts/catalogue.ts:327–365,454–469`), computes exact per-zone footprint union, and does not join pallets/products. The control query duplicates the building read and up to two presence ranges. Its presence queries are appropriately bounded. The occupancy scan remains potentially byte-heavy with large active inventory, but historical released placements are excluded by status.

Remedy: expose one row-state query carrying exact occupancy and current status/version/blocked, and feed its control result to the toggle on catalogue rows. Do not couple a status-only toggle on a detail page to a broad occupancy scan unnecessarily. Existing read permissions match; mutations retain their transactional occupancy checks. If active placement bytes are actually large, consider an exact per-zone occupancy projection only after measurement: union is not additive across overlapping/stacked rectangles, so naive area counters are incorrect and projection maintenance adds writes/drift risk.

Verify: loading/error states, permission skips, archived and draft controls, mutation conflict tokens, and footprint parity with stacked/move/location-only placements. Measure unique executions and cache hits for a normal two-building page as well as a stress page. High per-row calls can justify merging even without proving high I/O.

### 4. Building inventory performs two active-move queries per distinct pallet and launches them together (P2, capacity-sensitive)

`convex/storageLayouts/catalogue.ts:515–568` correctly scopes active placement reads to one building, then calls `readMoveOccupancy` with its pallet IDs. `convex/storageLayouts/moveOccupancy.ts:16–36` deduplicates IDs but still issues RESERVED and IN_TRANSIT queries for each pallet in one `Promise.all`. Pallet/product joins are memoized (`catalogue.ts:81–95`).

For N distinct pallets and P distinct products, handler ranges are approximately 3 + 2N + N + P, before auth/target checks and adapter details. A 1,000-pallet, 20-product hypothetical building has approximately 3,023 handler ranges even with no active moves; empty indexed results still cost ranges, though their byte cost differs from document reads. The two-status move stage also launches 2N operations. The documented 1,000 concurrent-I/O limit creates a separate risk near N>500, earlier than the approximately 1,360-pallet range-only estimate in the October 10 review. Whether all adapter/page operations overlap must be confirmed with runtime instrumentation; do not present an exact production failure threshold.

Remedy: bound concurrency immediately if representative inventory requires it; this addresses outstanding-I/O risk but not total ranges. If scale justifies schema work, denormalize source/target building IDs onto moves, with corresponding building/status indexes, and backfill active moves so both building holds remain visible. This exchanges two reads per pallet for a small fixed set of building move ranges and adds index/write storage. A warehouse-wide active-move scan can be worse for small buildings, so use measured selectivity rather than a blanket replacement. Avoid storing move state on source placements because their updatedAt conflict token is used by move logic.

Verify: range/concurrency budgets at 100/500/1,000/2,000 pallets, cross-building source/target parity and active backfill completeness. Current dataset size does not prove these scales are reached.

### 5. Stack toggles scan warehouse pallet history; job-scan searches read entire history (P2)

`convex/finishedGoods/workflow.ts:2342–2390` builds stack candidates from warehouse-code-index `rows`, whose helper calls `.all(10_000)` at `:66–73`, then filters retired/status/nonmeasured rows in memory. `src/features/finishedGoods/StackScreen.tsx:157` includes upper selection and rotation in query arguments, so each change opens a query that repeats this candidate scan. Schema at `convex/schema.ts:830–842` has no pallet warehouse/status index. History contributes read bytes despite being filtered out.

Remedy: split stable live candidates from selected-upper/rotation preview; add warehouse/status indexing (optionally active/retired discriminator if history predominantly shares STORED), preserve complete measured/nonretired/stack-capable candidates and memoize legacy product fallback. New indexes incur storage and write costs; compact response rows mainly reduce network/result work, whereas indexing reduces scanned DB documents. Verify candidate parity and that rotation reads no warehouse candidate list.

Separately, job-scan substring search reads full documents using `.all(10_000)` and offset-pages only after filtering (`convex/finishedGoods/jobScans.ts:405–422`); current callsite is `src/features/finishedGoods/jobScan/JobScanRecords.tsx`. Nonsearch uses native paging and is already bounded. Each search page repeats the history scan, including large optional AI payloads. `.all` explicitly throws beyond the configured bound (`convex/lib/tenantDb.ts:604–623`); these paths are bounded-with-failure, not literally unbounded. Byte limits may arrive earlier depending on payload size.

Remedy: compact per-field normalized search projection, bounded cursor scanning and hydration only of matches, with transactional maintenance and resumable backfill. Preserve existing per-field substring/Thai semantics; a full-text index is not automatically equivalent. An initial simpler bounded scan over existing rows avoids the 10K failure but still reads AI payloads. Verify mapped filters, ordering, save/assign/delete/search parity and sparse common searches at growing history sizes; measure bytes per page.

### 6. Summary mutation flush repeatedly reads/patches the same product and adds tracking reads (P2, batch-specific)

`convex/lib/finishedGoodsSummary.ts:79–134` reconciles each pallet contribution, loading ledger+pallet, optional IN_TRANSIT move, then removing/adding product summary deltas. The flush reconciles touched pallets serially (`:281`). Tracking reads rows before and after patch/replace (`:263–273`); move tracking reads the move again (`:242–248`). Batches can touch many pallets in one authorized mutation (`convex/finishedGoods/batches.ts:296–325`, `batchManagement.ts:185–200`); their package bound limits actual work, so this is not an unlimited fanout claim.

Remedy: load contributions with bounded parallel reads, aggregate removals/additions by product, patch each product summary once, and retain exact nonnegative/drift checks and idempotent ledger writes. Reuse tracked row data or safe immutable warehouse/pallet identity rather than rereading unchanged associations. Never parallelize independent-looking summary patches that target the same product without merging deltas. The concrete expected benefits are fewer database API/syscall invocations, summary/tracking reads and sequential await chains; latency and billed read savings require execution measurements. Convex queues database changes and commits the mutation as one atomic transaction, so multiple same-document patches do **not** establish multiple physical writes or proportional billed write bytes. Write-byte savings need transaction/usage metrics. This does not remove cross-mutation contention on popular product summaries. See [Writing Data](https://docs.convex.dev/database/writing-data#bulk-inserts-or-updates).

Verify: maximum-size replacement batch, moving/retired contributions, intentionally corrupted ledger and exact full-recompute parity. Instrument DB calls and OCC retries; do not equate code-level patch count with billed bytes without execution statistics.

### 7. Eligibility and batch unit-state checks scan released placement/move history despite existing status indexes (P2 quick win)

Follow-up inspection: `convex/finishedGoods/scanning.ts:30–63` (`eligible`) and `convex/finishedGoods/batchManagement.ts:42–80` (`unitState`) each load three complete histories: placements by pallet, placements by support pallet, and moves by pallet. They use the non-status indexes and `rows(...).all(10_000)`, then apply `.some`/`.find` for active records. Existing composite indexes are already available: placement `by_orgId_palletId_status` and `by_orgId_supportPalletId_status` (`convex/schema.ts:862–870`), and move `by_orgId_palletId_status` (`:1035`). Schema restricts placement statuses to RESERVED/STORED/RELEASED (`:76–80`), so “not RELEASED” is exactly the two active statuses.

Remedy without schema/backfill work: query `.first()` for each active status on those composite indexes, preserving tenant reads. Boolean eligibility needs only whether any of these six presence checks found a row, so ordering has no effect. A long history is replaced by at most six active document results/ranges; this may increase ranges from three to six for a brand-new unit with no history, but prevents all released/completed history from adding documents/bytes or reaching the 10K guard. It also narrows reactive dependencies away from inactive-history changes. Short-circuit after a blocking category if useful, but do not unnecessarily serialize all independent reads.

`unitState` requires extra care: it prioritizes SUPPORTING, then MOVING, then the unit's STORED status, then RESERVED/current placement. Preserve this reason precedence. It additionally exposes `moveStatus` even when SUPPORTING won, so skipping the move read on supporting units would change output. Its current `.find` chooses the first active move in the original pallet index's ordering. Taking RESERVED first unconditionally could change the returned representation if both active statuses exist. Fetch the first move of each active status and select whichever would be first in the original index order (including its tie behavior), or enforce/verify an existing single-active-move invariant before using arbitrary status precedence. Keep returning only `moveStatus` as today; a new full move object is unnecessary. Presence of placements/children is boolean and has no ordering concern.

Verify/measure if implemented: empty/new units versus deep released/completed histories, both RESERVED and STORED physical holds, supporting-plus-moving precedence, hypothetical dual-active-status moves, and original move order parity. Measure docs/bytes/ranges for scanning and maximum-50-unit batch reads; six narrow ranges per unit is still bounded fanout and should use controlled concurrency. No tests or source changes were made for this follow-up.

## Already fixed / false positives

- September geometry/inventory separation remains intact. Inventory reads do not fetch floors/zones/positions/blocks; layout reads do not fetch placements/pallets/products/moves. Preserve this useful cache boundary.
- Pallet/product and location parent memoization from `docs/plans/catalogue-query-optimization.md` is present. Do not repeat its previously measured 100→1 or 40→2 improvements as remaining work.
- Presence checks use narrow status indexes and `first()`. Lowering result limits cannot improve them materially.
- Per-product summaries are materialized already. The missing optimization is warehouse totals/readiness, not creating product summaries from scratch.
- Catalogues use bounded cursor scans. A sparse search or custom sort can still require multiple calls, but pagination is already implemented and exact global sorting requires evaluating relevant rows unless supported by an equivalent ordered index.
- Legacy full-building/get-floor/location-map/list endpoints remain for compatibility. Current API reference definitions alone do not establish live frontend usage; inspect dashboard traffic and rollback compatibility before removing them. The historic getStorageBuilding I/O is not evidence all current scenes still use it.
- No recommendation to remove auth, make all subscriptions imperative, estimate exact occupancy, truncate destination candidates, or persist browser inventory snapshots is justified.
