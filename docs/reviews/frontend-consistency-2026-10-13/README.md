# Frontend UI/UX consistency and component reuse audit

Date: 13 October 2026. Status: research and migration proposal only. No implementation is included.

The highest-value next step is to finish adopting the existing UI system and fix a few inconsistent interaction contracts. The app already has shared buttons, field layouts, page containers, dialogs, pagination, loading states and pointer-aware density. Replacing those foundations would add work and risk. The clearest new reuse boundary is camera acquisition; the next is the storage rectangle editor's presentation. The final plan contains 18 issue groups, with three P1 priorities.

## Scope and evidence

The initial inventory covers **335 source files, 40 page routes and 54,703 source lines** under `src`, excluding tests and `_prototype` assets. This includes server/API/support files for completeness. Every route and frontend family was inventoried; the researchers read main render paths, related state ownership and shared dependencies, and used repository-wide searches to find competing implementations. This is not a claim that every geometry line or every rendered state was manually verified. See [coverage inventory](coverage.md).

Independent research:

- **Kiro CLI**, `claude-opus-5.5`, high effort: architecture/reusability. [Original report](kiro-architecture.md).
- **Sol 6.1**, `gpt-6.1-sol`, high effort: UI/UX consistency. [Original report](sol-ui-ux.md).
- **Consolidation**: source checks of reported problems, existing abstractions, current tests and bounded live browser inspection. The agents researched separately before consolidation.

The audit uses the existing dirty working tree, including new HR screens and shared-control changes. Other work continued during the audit: job-scan tests and then navigation/workflow-step code and direct-link fallback props changed. Those edits were retained and were not made by this audit. Line references identify the inspected version; recheck them before implementation. Earlier October 10–12 plans and screenshots are context, not proof of current behavior.

The T3 preview loaded the frontend and public pages. The configured local Convex backend at port 3211 refused connection, so authenticated feature content remained in its loading state. Desktop/mobile shell findings have current browser evidence; camera, data, write and map findings are source-backed and still need connected runtime checks. No seed, backend deployment, write workflow, build or application test suite was run. The static Impeccable detector reported zero findings across the initial 335-file set; that does not establish accessibility, performance or visual compliance. [Evidence record](evidence/audit-evidence.json).

### A01 — Make ticket-camera framing truthful and recovery consistent

**P1 · M · Source-confirmed; device verification pending.**

**Problem and locations.** [src/features/finishedGoods/jobScan/PhotoCapture.tsx:132](../../../src/features/finishedGoods/jobScan/PhotoCapture.tsx#L132) crops its video with a fixed portrait/landscape ratio and `object-cover`, but `:87` captures the entire native frame. A landscape feed on a portrait phone can include another ticket outside the visible preview. The same component suppresses `video.play()` rejection (`:72`), has no camera Retry, and uses a plain startup/error overlay (`:136`). Its hidden file input has no explicit accessible name (`:121`). Barcode and location capture already use native ratio, contained framing, live status and recovery: [src/features/finishedGoods/BarcodeCameraBox.tsx:121](../../../src/features/finishedGoods/BarcodeCameraBox.tsx#L121), [src/features/finishedGoods/jobScan/LocationPhotoCamera.tsx:39](../../../src/features/finishedGoods/jobScan/LocationPhotoCamera.tsx#L39).

**Proposal and benefit.** First fix PhotoCapture's framing and playback/error states using the existing camera patterns. Then extract a small domain-local stream session hook and measured viewport from the two photo cameras. Expose start/retry/stop and truthful readiness; stop late-granted streams on cancellation. Keep barcode decoding/torch in `useBarcodeCamera.ts`, ticket queues and explicit AI submission in PhotoCapture, and single-location capture/review in LocationPhotoCamera. Reuse Notice, Button and localized labels. This removes divergent camera lifecycle fixes without coupling three different workflows.

**Validation.** Match preview to captured image for native 4:3/16:9 feeds and rotated phones; simulate play rejection, denied permissions, delayed grant/canvas completion, unmount, retry and double shutter. Retry retains selected photos. Preserve the ticket queue/size limits and location pixel limit. Inspect the file input's accessible name and live status, then test on a physical phone.

### A02 — Protect pending edits and creation drafts consistently

**P1 · M · Source-confirmed.**

**Problem and locations.** [src/features/storageLayouts/StorageZonesPanel.tsx:423](../../../src/features/storageLayouts/StorageZonesPanel.tsx#L423) accepts dismissal while a mutation is pending. Its X, Cancel (`:609`), inputs and drag callbacks remain usable; Save alone reflects pending (`:625`). The command snapshots values at `:333`, then success clears the editor at `:375`, potentially discarding edits made after submission. NewBuildingContent in [src/features/storageLayouts/StorageLayoutScreens.tsx:369](../../../src/features/storageLayouts/StorageLayoutScreens.tsx#L369) has no draft guard or pending form lock; Back stays enabled (`:461`). [src/features/finishedGoods/jobScan/AddLocationForm.tsx:108](../../../src/features/finishedGoods/jobScan/AddLocationForm.tsx#L108) locks fields but leaves Cancel enabled (`:259`). These differ from [src/features/finishedGoods/BatchManager.tsx:154](../../../src/features/finishedGoods/BatchManager.tsx#L154) and [src/components/ui/ConfirmDialog.tsx:66](../../../src/components/ui/ConfirmDialog.tsx#L66).

**Proposal and benefit.** Adopt the existing non-cancelable-write policy: freeze inputs and geometry interactions, make all dismissal paths agree, announce pending, and keep values/recovery after failure. Register meaningful creation drafts with existing draft/navigation guards. Explicit settled Cancel may intentionally discard, but should follow one documented creation-form policy. Keep permission revocation authoritative and preserve exact request identity; a hidden dialog does not cancel a backend command. This prevents misleading cancellation and later edits disappearing.

**Validation.** Defer success/failure and attempt Escape, overlay, X, Cancel, Back, route/warehouse/locale changes and dragging. The submitted payload stays fixed, no duplicate command fires, and failure retains the user's values. Recheck the ongoing workflow-navigation changes before implementing. Reserved-area local draft editing is synchronous and does not automatically need the same pending policy.

## Consistency guidelines

These standards preserve the current design direction and colors.

| Concern               | Standard                                                                                                                                                                                                                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Control density       | Keep **48px touch targets**; compact to **36px only at >=768px with a fine primary pointer**, using the existing `dense:` variant. Compact text/padding rather than shrinking touch targets. Input text stays 16px in touch mode. The switch's small visible track has an expanded hit area; do not judge it by track height alone.                                  |
| Spacing               | Reuse existing **2px label / 8px related fields / 16px sections / 24px task groups** tokens. Preserve necessary table and scene spacing; remove duplicate stacked actions before reducing every gap.                                                                                                                                                                 |
| Page widths           | `compact` for short tasks, `form` for ordinary forms, `wide` for bounded catalogues/HR, `full` for floor/scene workspaces. Align the header and task to the same boundary for an ordinary form. Keep a wide scene plus narrow inspector when the task requires it.                                                                                                   |
| Surfaces              | One framed task surface; inner groups use `Panel appearance="plain"` or `"divided"`. Avoid adding a card around an existing card solely for grouping.                                                                                                                                                                                                                |

QR/help/short confirmations usually fit sm; regular review md; visual editors justify lg/wide or one explicit shared editor size if the two existing 64rem editors need it. Different tasks need not have identical widths.                                                             |

For an in-flight non-cancelable write, keep the existing pending protection, announce progress, and retain recovery on failure. Permission revocation and context invalidation stay authoritative.                                                             |
| Form validation       | Shared visible label and linked hint/error; native `required` where appropriate plus `aria-invalid`/description. Show the actual failed condition. Keep decimal input drafts as strings until the owning domain validates/converts them.                                                                                                                             |
| Icon semantics        | `ScanIcon` for barcode/QR decoding; Camera for taking a photo; ImagePlus for file/gallery choice; Sparkles for AI processing; QR glyph for showing a QR label; Pencil for edit. Use one agreed internal-open arrow; ExternalLink only when the behavior warrants it. Decorative icons are hidden from assistive technology; icon-only actions retain names/tooltips. |

## Findings deliberately not promoted to global refactors

- Density, stronger badge inks, invalid field edges, basic scan glyphs, sidebar Search/AI Search trigger shape and warehouse leading icons are already largely standardized in the current tree. Do not repeat those migrations from old plans.
- A different QR/photo/geometry dialog width is not automatically a defect. Standardize the selection rule and eliminate unexplained overrides.
- `useHrWrite`, finished-goods retry/draft logic, and reserved-area versus storage-zone save semantics must remain separate.
- Shared UI already has protections for disabled links, focus return, empty/denied/loading states and sticky-footer inset. Extend adoption and tests instead of replacing working behavior.
- Map physical-area colors, theme-specific scene tokens, geometry labels and QR/camera backings are purposeful. No broad recoloring is recommended.
- Reference/prototype screens are not everyday production workflows. The routed floor demo is a demo; unimported reference art does not justify a production redesign.
- Public content's English language region and the self-contained bilingual fatal-error page are intentional. A public-facing operator name versus the product name is a content-policy question, not permission to rewrite legal facts.
