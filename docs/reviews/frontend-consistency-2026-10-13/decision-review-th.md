## ข้อเสนอหลัก

เริ่มจากความถูกต้องของภาพถ่าย การล็อกข้อมูลระหว่างบันทึก และขอบเขตคำสั่งเปลี่ยนสถานะอาคาร จากนั้นแก้ข้อความผิดพลาดและปัญหา shell ที่มีหลักฐานชัด การรวมคอมโพเนนต์ควรตามหลังการแก้พฤติกรรม และทำเฉพาะส่วนที่มี contract เดียวกัน

ตารางนี้ประเมินใหม่จาก [audit รวม](README.md), รายงาน [Kiro](kiro-architecture.md), [Sol](sol-ui-ux.md), source ปัจจุบัน และภาพ evidence เดิม ไม่ถือว่าการเห็นโค้ดซ้ำหรือไฟล์ยาวเป็นหลักฐานว่าผู้ใช้มีปัญหา รายละเอียดการตรวจกลุ่มความเสี่ยงอยู่ใน [current-source-validation.md](current-source-validation.md)

## วิธีอ่านความมั่นใจ

- **สูง:** ยืนยันเงื่อนไขจาก source ปัจจุบัน หรือมีภาพ/ผลทดสอบตรงจุด ไม่ได้แปลว่าทดสอบครบทุกอุปกรณ์หรือทราบความถี่ที่เกิดใน production
- **กลาง:** ยืนยันโครงสร้างหรือความต่างได้ แต่ผลกระทบต่อผู้ใช้หรือวิธีแก้ที่เหมาะสมยังต้องดู runtime/การใช้งาน
- **ต่ำ:** เป็นข้อเสนอด้านความสม่ำเสมอหรือการดูแลโค้ด ยังไม่มีหลักฐานว่าทำให้งานของผู้ใช้เสีย

ความมั่นใจในตารางหมายถึง **มั่นใจว่าเป็นปัญหา** ไม่ใช่ความน่าจะเป็นเชิงสถิติ ไม่ใช้เปอร์เซ็นต์ที่ไม่มีข้อมูลวัดรองรับ

## เหตุผลจากแหล่งข้อมูลต้นทาง

- การแยกเหตุผลผิดพลาดของ geometry สอดคล้องกับการระบุข้อผิดพลาดให้ผู้ใช้รู้ว่าข้อมูลใดผิดและผิดอย่างไร ไม่จำเป็นต้องสร้าง validation framework ใหม่ [W3C: Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)
- Page changes, pending และ connection feedback ควรประกาศอย่างเหมาะสมโดยไม่ย้าย focus เพื่อให้ผู้ใช้ assistive technology รับรู้สถานะ [W3C: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- ความ compact ไม่ใช่เหตุผลให้ลดพื้นที่กดทุกปุ่ม WCAG 2.2 AA กำหนดขั้นต่ำ 24×24 CSS px พร้อมข้อยกเว้น และอธิบายว่าพื้นที่กดใหญ่ขึ้นช่วยผู้ใช้; 48px ของแอปเป็นมาตรฐานการใช้งาน touch ของโครงการ ไม่ใช่ตัวเลขขั้นต่ำ AA [W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- ตรวจ ordinary form content ที่ 320 CSS px และ zoom; map/table ที่จำเป็นต้องเป็นสองมิติมีข้อยกเว้น จึงไม่ควรบังคับทุกพื้นที่ให้ใช้ layout เดียว [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Visibility, error prevention, consistency และการลดข้อมูลเกินจำเป็นเป็น heuristics สำหรับตัดสินใจ ไม่ใช่หลักฐานว่าทุก component ที่ต่างกันต้องรวม [NN/G: 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)
- Convex `useQuery` คืน `undefined` ตอนเริ่มโหลดและเมื่อ skip; query result object แยก pending/success/error ได้ จึงไม่ควรตีความ undefined หรือเวลาโหลดนานว่า denied/empty และ error branch ปัจจุบันไม่เท่ากับ transport disconnect feedback [Convex React](https://docs.convex.dev/client/react/overview)

ข้อเสนอการแก้และลำดับด้านบนเป็นการประเมินจากหลักฐาน ไม่ใช่ข้อกำหนดว่าต้องเปลี่ยน UI เป็นแบบใดแบบหนึ่ง และยังไม่ได้รับรอง WCAG compliance ของทั้งแอป

## Verification และข้อจำกัด

รอบนี้อ่าน current source, caller guards และ tests พร้อมตรวจภาพ shell ที่ audit เดิมเก็บไว้; ผล targeted tests ที่รันใหม่บันทึกใน [validation note](current-source-validation.md) ไม่ได้รัน build/full suite หรือเริ่ม backend และไม่มีการตรวจ end-to-end ใหม่ของ authenticated write/camera flows
