## Platform constraints and version scope

The reviewed package pins are Convex **1.46.0**, `convex-test` **0.0.54**, Clerk Next.js **7.7.4**, backend **3.16.4**, and testing **2.2.22**. [Packages][packages] Current official documentation was consulted on 2026-11-03 as platform context, not as a version-pinned API migration proposal:

- Convex documents that `convex-test` does not enforce size/time limits, has simplified search semantics, and does not run cron jobs. Its results still establish application logic. The repository's byte meter approximates returned document size using JSON length. [Convex limitations](https://docs.convex.dev/testing/convex-test#limitations), [meter][meter].
- Scheduled functions are durable across restarts; scheduling from mutations is transactional. This supports the design but does not prove that this application's deployed cron fired and drained its backlog. [Convex scheduling](https://docs.convex.dev/scheduling/scheduled-functions).
- Production enforces document, transaction read/write, index-range and execution-time limits; capacity also depends on deployment class. Capture actual backend measurements; do not treat local JSON byte counts or whole-test duration as production latency. [Convex limits](https://docs.convex.dev/production/state/limits).
- Clerk reverification requires an eligible configured factor and application-side handling. Session-token `fva` describes factor age in minutes, alongside issuance/session claims. Test the configured provider flow on the pinned application, without introducing new SDK APIs based solely on current docs. [Clerk reverification](https://clerk.com/docs/guides/secure/reverification), [session tokens](https://clerk.com/docs/guides/sessions/session-tokens). The existing caller already uses `useReverification` and a fresh Convex-template token. [Caller][clerk-caller]

### 1. Establish cloud payslip migration completion — R, highest operational priority

**Already covered:** integration checks resumed/repeated pages, two tenants, ownership, corrupt bytes/length, both-copy and missing-copy cases; local real backend migrated one PDF and preserved its hash through restore. [Payload tests][payload-migration-tests] [Validation][validation]

**Gap and scenarios:** cloud counts and completion are unavailable. First inventory each relevant cloud deployment with a complete dry-run traversal. If rows require migration, follow the existing migration procedure as separately authorized execution, retaining checkpoints and verification results. In a disposable real backend, extend the one-PDF evidence to multiple full eight-row pages across two synthetic tenants, with interruption, duplicate page delivery and a corrupt row. The migration scans the table across organizations; tenant correctness comes from each row/payload association. [Migration implementation][migration]

**Pass oracle:** fresh full verification from empty cursor reaches `isDone`; sum `scanned` and `alreadyMigrated`, require `inline=0`, `missingPayload=0`, and no integrity failures. Independently reconcile statement/payload ownership and retained original hashes. A corrupt row is reported and unchanged; repeated pages do not duplicate payloads. If there are zero rows, record measured zero. Legacy unmigrated downloads/publication may deliberately refuse; do not certify readiness from metadata alone. [Completion rule][migration-guide]

**Environment/priority:** cloud read-only evidence first; migration mechanics on disposable real backend. Required before declaring cloud payslips ready or removing compatibility fields. No migration was performed by this research.

**Gap:** helper tests cover expired/future/permanent receipts, but the exact-equality claim is weaker than its title: the boundary case uses a moving wall clock without freezing `Date`, so the check may execute after the intended instant. Add a deterministic frozen-clock assertion. A broad **caller-level delayed-retry matrix** is also missing. `expiresAt <= now` means fresh execution at and after expiry, independent of sweep timing. Ordinary receipts last 30 days; permanent HR cancellation fences are a separate contract. Never require expired ordinary keys to deduplicate forever. [Helper][idempotency] [HR envelope][hr-command]

[Scheduler tests][scheduler-tests] [Sweep tests][expiry-tests] [Validation][validation]

**Gap and scenarios:** record an actual deployed 03:00 UTC cron invocation and its scheduled chain. On a disposable real backend, seed more than 2,000 eligible records per tenant/table, multiple organization pages, newly expiring records during execution, interrupted/restarted service and repeated dispatch. Observe several daily passes with arrivals below, near and above the cleanup budget.

**Pass oracle:** fixed-cutoff isolation, no future/permanent deletion, every organization reached, bounded work per transaction, correct backlog reporting, and later passes progress from surviving records. Arrival rates above this budget need an explicit capacity decision, not a test expecting impossible steady-state drainage. [Retention implementation][retention] [Cron][cron]
