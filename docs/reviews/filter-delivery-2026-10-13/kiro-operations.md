## Compatibility

- `listJobScans`: verified above for the request shape of the previous frontend. A numeric offset search cursor from a tab loaded before release (e.g. `"20"`) answers `{ items: [], isDone: true, continueCursor: "" }` (status `reset`), so the old page shows no rows and no dead Next; Previous returns to the user's earlier pages. Unfiltered native cursors from old tabs still resume (tested). With the old client, sparse searches can show short or empty pages with Next; that is honest continuation, not loss.
- `getPallet` and `stackOptions` keep their previous responses for old clients. New arguments are optional; the public contract refresh recorded additions only (`UPDATE_PUBLIC_CONTRACT=1` refuses breaking changes).

## Finite domains and exceptions (actual write or domain bounds)

- Batch unit editor: active units per batch are bounded by `MAX_FG_PACKAGES` = 50, enforced by packing validation and by `repackAvailable` (retained + new ≤ 50). Repack validation needs the complete active set; it is not split.
- AI operation attempts: `MAX_ATTEMPTS` = 2 per operation (write contract).
- Stack children of one support: one pallet per level, ≤ 10 levels (`validateStack`).
- Packing/repacking drafts and one location-only assignment receipt are single editing drafts/records.

Not finite (read caps, stated as gaps below): the AI summary's 3,000-row aggregate budget, the report's 200/100 label lookup, `activeMovesOf`' 100-row capacity check per status, and the 10,000-row `rows()` capacity in legacy and batch reads.

## Unresolved gaps

- **Substring search is still a scan.** Saved-scan, stack-choice and option search cost one request per 100 rows until a page fills. A sparse match in 10,000 records takes about 100 sequential requests; rows appear as found and progress is shown, but time to a settled empty result is proportional to history. A faster result needs a maintained search projection (n-gram/posting) with backfill.
- **Destination recommendations are computed over every zone.** `recommend`/`recommendMove` still read the warehouse's zones and build each location context before ranking globally. The picker's paging bounds rendering only; it does not reduce backend reads or first-candidate latency. Paging the computation would change the global recommendation unless a ranked projection is maintained.
- **Catalogue custom sorts** (`catalogue.page` with a comparator) still scan the whole range for each page. Traversal is bounded per request and correct; a faster identical global order needs maintained sort indexes or projections. Not attempted; local paging would not change this backend work.
- **Batch units still read retired units** before filtering (`by_orgId_preparationBatchId`, capacity 10,000). Avoiding them needs either `eq(field, undefined)` support in the tenant index adapter (owned by the location worker; it rejects undefined values today) or a new maintained active marker with backfill, which would make an optional-field backfill a deployment step. Deferred; recorded for the adapter owner.
- **AI aggregate completeness.** The summary still reads at most 3,000 rows and reports `complete: false` beyond it; presentation paging does not complete a partial aggregate. Model and environment filter options are still derived from those rows, so with an incomplete summary they may omit values. Actor options are listed in user-ID order, not alphabetically (no name index on the global users table).
- `workflow.list` (unused by the UI) and the legacy `stackOptions` still read whole warehouse collections; remove after the rollback window.
