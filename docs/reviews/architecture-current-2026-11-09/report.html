A smaller, explicit architecture

Keep the existing Next.js, React and Convex application. Improve the seams developers change most: typed feature interfaces, pure domain rules, explicit transactional writers and clearly owned UI drafts.

Implementation is based on current evidence.

The original audit used an older checkout. Several claims were already fixed or did not reproduce. Codex and Kiro investigated the findings; Kiro repeatedly stalled, so Codex reviewed and completed the structural slice. The completed changes are grouped into three PRs, within the five-PR limit.

#149 · Tooling and dependencies (merged) · #150 · AI quotas and owned attachments (merged) · Structural changes and this report: current PR.

Architecture and data flow

1. Feature UI

Routes and screens compose feature adapters, draft reducers and reusable components.

User intent → version-bound draft → one live command owner

2. Feature functions

Convex functions validate inputs, authorize the tenant and call pure domain rules. Feature commands own replay and write policy.

Validated request → rules → source write + receipt + projections

3. Storage and integrations

Convex stores authoritative rows and derived read models. Clerk supplies identity; UploadThing assets require verified ownership. AI calls consume quotas first.

Atomic commit → reactive query → inferred UI result

Keep one deployable application and the current transactional backend. No evidence calls for microservices, another database, a new state framework or a wholesale runtime replacement. The module map names owners, allowed imports and verification commands.

Next implementation steps

1 · Finish the reviewed structural PR

Run both type checkers, normal lint/format, codegen freshness, registered contracts, navigation gates, actual caller/browser tests and the full suite. Merge only after the required aggregate CI gate passes. Preserve the already-merged security work during integration.

2 · Verify the external upload path before release

Set matching Next/Convex UploadThing credentials; the deploy preflight refuses missing or mismatched credentials. Exercise a real staging callback, cross-tenant attachment refusal and abandoned-upload cleanup. Check the actual CDN delivery/ACL policy against the intended privacy requirement. Local tests cannot prove that live policy.

3 · Extend typed contracts when changing a feature

229 of 234 public results still contain any. Follow the two pilots: explicit result validator → inferred client result → table-derived document access → ID-preserving feature reference. Accept a slice only with registered wrong-shape/input cases and compile-time wrong-table checks. Avoid a second mirrored DTO/error system.

4 · Measure scale before changing the architecture

Capture per-feature read counts, transaction sizes, latency, projection conflicts and provider spend on realistic fixtures or staging. Consider partitioning only when a repeatable budget violation exists. Raise HR limits only after staged close and history-refusal budgets are demonstrated. Compare checker time and defects caught before removing a lane.

How to keep changes safe

Declare inventory projection ownership at the mutation. Keep domain models free of persistence imports. Reuse receipt mechanics while preserving feature policies. Keep drafts, pending operations and Back entries under explicit owners. Remove interfaces with a caller inventory; prelaunch permits deliberate breaking cutovers and fresh data, so historical snapshots should not dictate the current model.
