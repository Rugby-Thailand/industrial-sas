## Best next experiment: preinstalled browser dependencies

Playwright's official Docker image contains browser executables and their OS dependencies. A version match with the repository's Playwright package is required; the currently displayed documentation examples use a newer version and should not be copied verbatim. The candidate for this commit is `mcr.microsoft.com/playwright:v1.62.1-noble`, pinned by digest. [Docker guidance](https://playwright.dev/docs/docker)

The official registry was checked directly. The tag exists; its index digest is `sha256:dcc5531e97840b9b5e794f2814476b21571c5124a3fca2267d73041f56e7580e`. The amd64 manifest is `sha256:c091b21d9fae78c76e85cd4356431e9b018402f172a214fc7d7a5e9a7e29d8ac`; its seven compressed layers total **949,411,114 bytes, approximately 905 MiB**. This is a benchmark candidate, not a guaranteed speedup: cold image pull and extraction must be included. A managed ephemeral runner with dependencies already installed is another candidate, with separate provisioning cost. ## Other options

| Option                   | Applicability and limits                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cache browser binaries   | Poor match: binaries downloaded in approximately 13 seconds; Linux dependency work dominated. Playwright explicitly discourages ordinary browser caching because restore time can match download time and Linux OS dependencies still need installation. [CI guidance](https://playwright.dev/docs/ci#caching-browsers)                                                                                                                                                                   |
| More navigation shards   | Technically supported because `fullyParallel` allows individual tests to be distributed, even within the one spec file. Ordinary sharding repeats each runner's setup; it cannot remove the observed apt bottleneck. Even ideal two-way division of the entire 33-second test step saves only 16.5 seconds before added overhead. [Sharding](https://playwright.dev/docs/test-sharding)                                                                                                   |
| Split by browser project | Could reduce the dependency set per runner, but WebKit still requires its Linux dependencies and each job repeats setup. Prefer measuring preinstallation first. Keep all four projects and unique artifact names if later split. Project selection is supported with `--project`. [Browsers](https://playwright.dev/docs/browsers#run-tests), [artifact names](https://github.com/actions/upload-artifact#not-uploading-to-the-same-artifact)                                            |
| Increase workers         | Does not accelerate apt. Playwright recommends conservative CI worker counts and sharding for wider parallelism. Benchmark only after setup is fixed; the server and browsers compete for runner resources. [CI workers](https://playwright.dev/docs/ci#workers)                                                                                                                                                                                                                          |
| Reuse an existing server | Not a setup optimization here. `reuseExistingServer` uses a process already listening in the same environment; it does not share a build/server across isolated jobs. Keep the explicit fresh server for this framework/history harness. [Web server documentation](https://playwright.dev/docs/test-webserver), [harness contract](https://github.com/Rugby-Thailand/industrial-sas/blob/a116f39d0c257d1e33ada96a497932c11668bf47/scripts/navigation-guard-preview/README.md)            |
| Remove reports or traces | Not supported by the measured bottleneck. Successful CI uploads JUnit; diagnostics upload only on failure. Keep diagnostic evidence. If future measurements identify report overhead, blob reports can support later merging; matrix artifacts require distinct names. [Workflow](https://github.com/Rugby-Thailand/industrial-sas/blob/a116f39d0c257d1e33ada96a497932c11668bf47/.github/workflows/quality.yml), [blob reports](https://playwright.dev/docs/test-reporters#blob-reporter) |

## Coverage must remain intact

The navigation harness imports the actual Next router/history integration and production navigation providers. It is distinct from production smoke and the Vite workspace suite. A Firefox-specific native traversal branch is already present; dropping Firefox/WebKit or replacing real browser history with mocked events would remove meaningful evidence. The suite uses per-test page state, route interception and session storage; its `beforeEach`/`afterEach` hooks do not create a shared page. Independent tests can remain parallel, but the ordered save/Back/query actions inside each regression must remain ordered. No redundant scenario or suite deletion was established.
