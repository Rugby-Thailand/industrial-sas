## Finding

The selected eight-core, preinstalled GitHub runner architecture is **not available on the current GitHub Free organization**. No usable existing eight-core Linux capacity was established. The current public repository already receives four-core standard GitHub runners, so the proposed eight-core pilot is a twofold core increase, not fourfold. The current Vercel team is Hobby. Neither platform offers an established five-second startup guarantee that supports the plan's release-readiness budget.

A zero-purchase experiment can use the current standard runners and optimize measured setup/sharding. It cannot honestly be described as a pilot of managed eight-core custom images. The paid infrastructure option below remains a proposal, and no under-120-second outcome is established.

## GitHub paid custom-image pilot

Custom images require GitHub Team or Enterprise Cloud, enabled image policy and runner/image administrative permissions. Larger runners also need a payment method and positive Actions spending limit. Their configured maximum concurrency is a scaling limit rather than reserved ready capacity. [Custom-image requirements](https://docs.github.com/en/actions/how-tos/manage-runners/larger-runners/use-custom-images), [runner requirements](https://docs.github.com/en/actions/reference/runners/larger-runners).

GitHub explicitly documents that the first larger-runner request may need a new VM. Following use, machines can become ready for subsequent runs within five minutes; a subset may stay warm afterwards depending on volume. This is **not** a five-second assignment/readiness SLA. Image preinstallation avoids per-job tool downloads but does not reserve warm instances or remove checkout, dependency verification/hydration, artifact transfer, queue time, or image preparation. [Warm-pool behavior](https://docs.github.com/en/actions/reference/runners/larger-runners).

Published USD prices checked today:

| Linux x64 eight-core job   |              $0.022 per runner-minute | Each job rounds partial minutes up. Public repositories and included standard minutes do not waive this charge. |
| Linux x64 sixteen-core job |              $0.042 per runner-minute | Optional comparison; no performance assumption.                                                                 |

[Team price](https://github.com/team), [runner rates and billing rules](https://docs.github.com/en/billing/reference/actions-runner-pricing), [image allowance and storage price](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Concrete budget illustration, **conditional on the target runtimes**: keep the tiny aggregate job on standard free compute, run the nine quality jobs plus one artifact builder on eight-core machines for up to 75 seconds each, then one release job for up to 40 seconds. That is `10 × 2 + 1 = 21` rounded runner-minutes, or **$0.462 per successful push**. Five comparable runs cost $2.31; twenty runs cost $9.24; twenty-five cost $11.55. Retries, failures, cold installs and image creation add usage. Assuming one billable Team seat, the corresponding base-plus-compute amounts are $6.31, $13.24 and $15.55 for that billing month, before image costs/tax; seat count is unverified. A hypothetical ten-minute image build costs $0.22. One hypothetical 100 GB retained image for a full month exceeds the 75 GB allowance by 25 GB and costs $1.75; two such versions cost $8.75. Actual snapshot size/build duration must be measured.

An owner-approved pilot would create a repository-restricted runner group and immutable image containing the exact Node/pnpm/Bun toolchain, locked Playwright browser revisions and Linux libraries; provision at least ten concurrent slots for the current initial lanes plus artifact preparation; keep mutation credentials out of image and quality jobs; retain `pnpm install --frozen-lockfile`; validate the image manifest at job start. Use a manual credential-free benchmark workflow first. Record request/assignment/start, all setup, suites, cache/lockfile misses, join and artifact transfer. Changing only `runs-on` cannot test the whole hypothesis.

Hobby currently uses Basic build machines: two vCPUs and 8 GB RAM according to the September 3, 2026 official announcement. Older cached docs contain conflicting Hobby/default and price figures; use the newer announcements rather than claiming existing Turbo capacity. [Current Basic/Hobby announcement](https://vercel.com/changelog/basic-build-machines).

Current published build rates are Standard four-core $0.014/minute, Enhanced eight-core $0.028/minute and Turbo thirty-core $0.105/minute. Thus a hypothetical one-minute Enhanced build uses $0.028, and Turbo uses $0.105 of usage; thirty one-minute builds use $0.84 or $3.15 before other usage consumes the credit. These are compute arithmetic, not measured build duration or a complete invoice. No upgrade or trial was started. [Pro price/credit](https://vercel.com/docs/plans/pro-plan), [April 2026 build pricing](https://vercel.com/changelog/reduced-pricing-for-turbo-build-machines).

Larger/on-demand Vercel builds address compilation and queueing, but do not accelerate GitHub quality jobs and do not supply preinstalled GitHub runners. A GitHub prebuilt artifact also makes larger Vercel compilation capacity mostly irrelevant to that path. Existing cold/warm deployment readiness and prebuilt provisioning remain measurements for the artifact/release spike; Vercel's generic prewarming description supplies no numerical readiness guarantee. [Build options](https://vercel.com/docs/builds/managing-builds), [build infrastructure](https://vercel.com/docs/builds).

## Minimal experiment within current authorization

Use existing public four-core `ubuntu-24.04` compute for a credential-free benchmark of the reviewed quality improvements and pure production build. Retain every quality suite. Count browser/tool cache restoration or container pull/extraction as setup rather than calling it zero installation. Test exact-lock and changed-lock/cold cases. Neither a cache hit nor a local Mac result proves eight-core Linux timing. If no current-capacity experiment can fit the 75-second preparation budget, record that stop condition and present the paid/custom-image proposal with actual billable seats, image size and job counts before any purchase. Even a passing 75-second gate must still demonstrate full push-to-live tail and representative p95 under 120 seconds before cutover.
