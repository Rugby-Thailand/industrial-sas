# EasePOS และ LINE: หลักฐานสำหรับวางแผน HR onboarding

ตรวจเมื่อ 2026-10-13 เพื่อวางแผนเท่านั้น ไม่แก้ EasePOS ไม่ deploy และไม่ส่งข้อความ LINE

**บริบทที่ยืนยันกับผู้ใช้:** row หมายถึงแถวพนักงานใน HR; bot ที่ assign คือผู้ช่วย HR และการแจ้งเตือน ส่วน process ลูกค้ายังเปิดไว้ ไม่ใช่ข้อสรุปว่าจะ assign พนักงานให้ customer-support bot

## LINE official docs ที่มีผลต่อแผน

1. **OA onboarding:** สร้าง/ใช้ LINE Official Account และเปิด Messaging API ผ่าน OA Manager; เลือก provider ให้ถูกตั้งแต่แรก เพราะย้าย channel/provider ภายหลังไม่ได้ อย่าบอกธุรกิจให้สร้าง Messaging API channel ตรงใน Developers Console แบบคู่มือเก่า [Get started](https://developers.line.biz/en/docs/messaging-api/getting-started/)
2. **OA connection ต่างจาก personal identity:** `userId` เป็น ID ของผู้ใช้ใน provider หนึ่ง ไม่ใช่ LINE ID ที่ผู้ใช้ตั้ง และไม่ใช่ phone/name; Login กับ Messaging API ใน provider เดียวกันได้ userId เดียวกัน แต่คนเดียวกันต่าง provider ได้คนละค่า [Get user IDs](https://developers.line.biz/en/docs/messaging-api/getting-user-ids/)
3. **Connect พนักงาน:** ทำได้ผ่าน verified LINE Login/LIFF หรือ Messaging API account linking; account linking ใช้ one-time link token อายุ 10 นาที + service login + random nonce + accountLink webhook ไม่จำเป็นต้องมี Login channel และต้องให้ unlink ได้ [Account linking](https://developers.line.biz/en/docs/messaging-api/linking-accounts/)
4. **LIFF เป็นหน้าพิสูจน์ตัวตน/ใช้งาน:** ส่ง access token หรือ ID token ให้ server ตรวจ; ห้ามเชื่อ userId/profile JSON ที่ browser ส่งมาเอง; access token ของ LIFF อาจถูก revoke เมื่อปิดแอป [LIFF user data](https://developers.line.biz/en/docs/liff/using-user-profile/)
5. **Webhook:** verify HMAC-SHA256 ของ raw bytes ก่อน parse ด้วย channel secret; event อาจซ้ำและมาผิดลำดับ ต้อง dedupe และใช้ event timestamp; เปิด redelivery ซึ่งค่าเริ่มต้นปิด แต่ไม่ได้รับประกัน delivery [Signature](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/), [Receiving messages](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)
6. **Reply กับ notification:** reply token ใช้ครั้งเดียว ควรใช้ภายใน 1 นาทีหลังรับ webhook; redelivery ใช้ไม่ได้หากเคยตอบแล้วหรือ event เกิน 20 นาที การตอบภายหลัง/แจ้งเตือนต้องออกแบบ push ตาม eligibility แทน [Reply API](https://developers.line.biz/en/reference/messaging-api/#send-reply-message), [Push API](https://developers.line.biz/en/reference/messaging-api/#send-push-message)
7. **ส่งซ้ำ/สถานะ:** push และ API ที่รองรับต้องใช้ stable `X-Line-Retry-Key` ตั้งแต่ครั้งแรก อายุ 24 ชั่วโมง; provider accepted ไม่ใช่หลักฐานว่าผู้ใช้ได้รับหรืออ่าน [Retry requests](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)
8. **Token operation:** long-lived token reissue ทำให้ตัวเดิมใช้ไม่ได้; LINE แนะนำ v2.1 สำหรับ bot setup จึงควรมี rotation/reconnect และ credential health ไม่ฝัง token ใน UI/HR row [Token types](https://developers.line.biz/en/docs/basics/channel-access-token/), [Build a bot](https://developers.line.biz/en/docs/messaging-api/building-bot/)
9. **History/media:** text อยู่ใน webhook และไม่มี API ดึง text เดิมกลับมา; media มีอายุบน LINE จึงต้องรับและเก็บตามนโยบายของระบบ; unsend ควรทำให้ข้อความเดิมไม่ถูกแสดงหรือใช้งานต่อ อย่าสัญญา import ประวัติแชทก่อนเชื่อม [Receiving messages](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)
10. **OA Manager กับ bot:** OA ใช้ greeting/auto-response ร่วมกับ Messaging API ได้ แต่ต้องกำหนดว่าใครตอบเพื่อหลีกเลี่ยงข้อความซ้ำ; webhook URL ปกติมี endpoint เดียวต่อ channel [Build a bot](https://developers.line.biz/en/docs/messaging-api/building-bot/)
11. **การตอบจาก OA Manager:** จาก event/endpoint specification ที่ตรวจ ยังไม่มีหลักฐานเพียงพอให้สัญญาว่า manual messages จาก OA Manager หรือประวัติของมันจะ sync กลับ inbox ของ Industrial SAS ครบ จึงเสนอให้ใช้หน้า chat ใน Industrial SAS เป็นแหล่งบันทึกการตอบ/ownership และทดลอง OA Manager interoperability ก่อนเพิ่มคำสัญญานี้; นี่เป็น **ข้อสรุปด้านการออกแบบจากขอบเขต API ที่พบ** [Messaging API](https://developers.line.biz/en/reference/messaging-api/)
12. **Multi-tenant:** API rate limits ใช้ต่อ channel; console จำกัด Admin-owned channels 100 ต่อ provider และ OA Manager account 100 OA ไม่ควรรวมธุรกิจที่ไม่เกี่ยวกันไว้ provider เดียวโดยไม่ออกแบบ ownership [API rate limits](https://developers.line.biz/en/reference/messaging-api/#rate-limits), [Console limits](https://developers.line.biz/en/docs/line-developers-console/overview/)
13. **One-click attach เป็นอีก capability:** LINE Module มี attach/authorization และ channel active/standby แต่เอกสารระบุเงื่อนไข corporate/paid LINE Marketplace extension ไม่ควรใช้เป็นสมมติฐาน MVP ทั่วไป [Module](https://developers.line.biz/en/docs/partner-docs/module/)

## ข้อเสนอที่ส่งต่อให้แผน Industrial SAS

- ใช้ pattern ของ EasePOS คือ **Settings ธุรกิจ → connection readiness → คนเชื่อมบัญชี → chat/notification** แต่ให้ HR employee row เป็นจุดเชื่อมบัญชีพนักงานตามที่ผู้ใช้ระบุ
- แยก 3 เรื่องใน model: **business OA connection**, **verified employee LINE binding**, **HR assistant assignment/notification subscription**; assigned bot ใน UI ไม่ควรหมายถึงการสร้าง OA/channel ใหม่ต่อพนักงาน
- HR row แสดง connection status, bot ที่ได้รับ, notification preference, และคำสั่ง connect/reconnect/unlink; QR ต้องชี้ employee + tenant + intended connection อย่างชัดเจน มี expiry และป้องกัน replay/ผูกผิดคน การมี QR อย่างเดียวไม่พิสูจน์ว่า scanner คือพนักงานคนนั้น
- เลือก account linking ถ้าต้องการ flow ใน OA โดยไม่สร้าง LIFF ต่อธุรกิจ; ถ้าใช้ LIFF ต้องให้ Login/Messaging channel อยู่ provider เดียวกัน และตรวจ token ที่ server พร้อม service employee authorization ทั้งสองแบบต้องให้เจ้าของตัวตนยืนยัน
- เปลี่ยนสิทธิ์เข้าถึง assistant และ notification เมื่อพนักงานย้ายไซต์/ยุติงาน/เปลี่ยน role จาก HR source of truth; binding ไม่ใช่สิทธิ์ permanent และ employee ที่ยังไม่มี system user ต้องมีขั้นตอนพิสูจน์ตัวตนก่อนเปิด HR data
- HR assistant กับลูกค้าเป็นคนละ conversation audience/policy; ฝั่งลูกค้าเก็บเป็น capability ภายหลัง จนกว่าจะรู้ process จริง และไม่ยก default-on marketing consent ของ EasePOS มาเป็นนโยบายลูกค้าของ Industrial SAS โดยอัตโนมัติ

**ข้อควรระวังเมื่ออ่าน schema EasePOS:** `provider = "line_messaging"` เป็นชื่อ adapter ([BE `marketing_channel_repository.go` L63–69](https://github.com/atiz-official/ease-international-backend/blob/325637b7bf9d4d23d39e16f4dab0a54116605458/internal/repository/postgres/marketing_channel_repository.go#L63-L69)) ไม่ใช่ LINE Developers Provider ID จริง; identity ถูก scoped ด้วย tenant + connection + provider label + line_user_id ([BE `marketing_inbound_repository.go` L292–331](https://github.com/atiz-official/ease-international-backend/blob/325637b7bf9d4d23d39e16f4dab0a54116605458/internal/repository/postgres/marketing_inbound_repository.go#L292-L331)) comment L294–295 ที่ว่า userId unique ใน channel แคบกว่าข้อเท็จจริง official ซึ่ง scope คือ provider จึงไม่ควรคัดลอก comment นี้เป็น domain rule และไม่ควรเก็บ `employee.lineUserId` global ช่องเดียวแล้วใช้ข้าม OA/provider
