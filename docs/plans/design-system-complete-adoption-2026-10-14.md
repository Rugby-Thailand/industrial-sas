## 0. สรุปสำหรับผู้อ่านเร็ว

ทิศทางที่ยืนยันแล้วคือ design sheet แบบเงียบ ไม่มี inner rail ตามต้นฉบับที่อนุมัติ: label ชิด control, focus แบบ restrained, task surface แบนและใช้ร่วมกัน, status ink เข้มขึ้น, ตัวเลขจำนวน tabular ชิดขวา, ไทย/อังกฤษ, light/dark และ field แบบ compact (32px/14px บน desktop ที่ ≥768px และ pointer ละเอียด; 40px/16px บนจอสัมผัสหรือจอเล็ก) ไอคอนในช่อง field ขนาด 16px อยู่กลาง ระยะขอบเท่ากัน และไม่มี hover decoration หรือการขยับตอนกด

ช่องว่างหลักที่ยังเหลือใน source ปัจจุบัน:

1. **ขนาด field ยังเป็น 48/36px** เพราะ `Input` และ `SelectTrigger` ใช้ token เดียวกับปุ่ม (`--spacing-touch` 3rem, `--spacing-control` 2.25rem ใน `src/app/globals.css`) ยังไม่มี token สำหรับ field 40/32px โดยเฉพาะ
2. **ไอคอนในช่อง field ยังเป็นปุ่ม ghost ธรรมดา**: `ScanCodeInput` ใช้ `IconButton` ghost ที่มี `hover:bg-raised` และไอคอน `size-5` (20px) ส่วนปุ่มล้างของ `SearchField` มีทั้ง hover และ `active:translate-y-px` จาก `buttonVariants`
3. **date/time/month ยังใช้ native picker 9 จุดใน 4 ไฟล์ HR** (แสดงผลจริง 16 instance) ยังไม่มี `calendar.tsx`, `popover.tsx`, `dropdown-menu.tsx` และยังไม่มี component สำหรับวันที่/เวลา
4. **Popover/DropdownMenu ใช้ Radix ตรง ๆ** ใน 8 ไฟล์ (Popover) และ 1 ไฟล์ (DropdownMenu) ยังไม่มีเจ้าของ primitive ร่วมกัน
5. **ไม่มี harness ใน browser จริงสำหรับ shared controls** jsdom วัดความสูง ตำแหน่งไอคอน การ portal หรือ scroll ไม่ได้ และหลักฐานใน preview ไม่ใช่หลักฐานของ application

### ข้อกำหนดเพิ่มเติม · 15 ตุลาคม 2026: สถานะของปุ่มข้อความ

ผู้ใช้ยืนยันว่า text button เปลี่ยนเฉพาะสีเมื่อ hover/กด: ไม่มีพื้นหลังใหม่ ขอบใหม่ ขีดเส้นใต้ใหม่ เงา หรือการขยับ ตอนไม่พร้อมใช้งานใช้ disabled ink และไม่ตอบสนองต่อ hover; ตอน pending คงตำแหน่ง/ขนาดและป้องกันการกดซ้ำ; keyboard `focus-visible` ยังมี outline ชัดเจน ไอคอนใน field ใช้กติกาเดิมคือไม่มี hover หรือ press effect

นำเข้า **DS-3** โดยแก้ `src/components/ui/buttonVariants.ts` สำหรับ text action แบบ `ghost`/`link`: เอา hover fill/underline และ inherited `translate-y-px` ออกจากกรณีที่เป็นปุ่มข้อความรวมข้อความพร้อม icon จัดสี rest/hover/pressed ผ่าน token ของธีม และคง disabled/aria-disabled/pending contract ของ `Button` ไว้ ระวัง `ghost` ที่เป็น standalone icon-only button หรือ menu/disclosure trigger; ต้องตรวจ caller เพื่อคง feedback ของกลุ่มนั้น ไม่เปลี่ยน selected/expanded ให้มีความหมายเท่ากับ hover

เพิ่มตัวอย่างและ assertion ใน harness ของ DS-1/DS-3 ทั้ง light/dark: rest → hover → pressed เปลี่ยนเฉพาะ computed color, geometry/background/border/decoration/shadow คงเดิม; keyboard focus เห็น outline; disabled/pending ไม่เปลี่ยนสีและไม่เรียก action ซ้ำ ตรวจ `button.test.ts`, `buttonActivation.test.tsx` และ caller ที่เปลี่ยนจริง ปุ่ม filled/outline, menu item และ passive status badge ไม่ได้รับกติกา text-only นี้

## 7. API ของ component (contract ที่จะ implement)

**Field geometry (`input.tsx`)**

- `fieldControlClassName` เป็นแหล่งเดียวของกล่อง field: ใช้ token field, padding 10px, text 16/24 (touch) และ 14/20 (dense), `focus-field`, invalid ใช้แค่ `aria-invalid:border-destructive`, disabled ใช้ token เดิม
- `InputAffordance({ side: "start" | "end", children })` เป็น slot สี่เหลี่ยม `aria-hidden` ไม่รับ pointer event และวางไอคอน 16px กึ่งกลาง
- `InputAction({ label, onClick, disabled, pressed?, haspopup?, children })` เป็น `<button type="button">` ใน slot เดียวกัน ไม่ใช้ `buttonVariants` จึงไม่มี hover และ translate มี `aria-label` และ title ข้อความเดียว รองรับ `aria-pressed` หรือ `aria-haspopup` (อย่างใดอย่างหนึ่ง เหมือน `ScanCodeInput` เดิม) มี inset focus outline และ disabled ตามจริง
- Input ที่มี slot จะได้ padding ด้านนั้นเท่าความกว้าง slot × จำนวน slot (แทน `pr-14`/`pr-26`/`pl-9` ที่ hard-code)

**`ScanCodeInput` / `SearchField`**: props เดิมทั้งหมดคงไว้ (`onScan`, `scanLabel`, `scanning`, `scanDisabled`, `scanDialog`, `trailingAction`, `onEnter`, `inputRef` …) เปลี่ยนเฉพาะการ render ภายใน ปุ่มล้างยังคืน focus ให้ input และ Enter ยังทำงานตามที่ caller กำหนด

**`SelectControl`**: API เดิม (`value`, `options`, `onValueChange`, `placeholder`, `emptyLabel`, `pending`, `invalid`, `describedBy`, `leadingIcon`, `size`) คงไว้ chevron และ `leadingIcon` ใช้ slot และ `SelectContent` ยัง portal ด้วย `position="popper"`

**`Popover` / `DropdownMenu` (`src/components/ui/popover.tsx`, `dropdown-menu.tsx`)**: สร้างจาก shadcn style `radix-nova` (`components.json`) แล้ว map ไป token ของ app (`bg-overlay`, `border-border`, `shadow-md` แบบ `SelectContent`, `max-w-[calc(100vw-1.5rem)]`, collision padding) โดย portal ไปที่ body เหมือนเดิม

**`DateField` (ใหม่, `src/components/ui/DateField.tsx`)**

- Props: `value: string` (`""` หรือ `YYYY-MM-DD`), `onValueChange(value)`, `label`, `id?`, `min?`, `max?`, `today` (civil ISO จากผู้เรียก), `required?`, `clearable?`, `disabled?`, `invalid?`, `describedBy?`, `placeholder`
- Trigger เป็น `<button>` ที่ใช้ `fieldControlClassName` มี `aria-haspopup="dialog"` และ `aria-expanded` แสดงข้อความ `formatBusinessDate(value, locale)` (ไทย: "14 ต.ค. 2569") และมี `InputAffordance` เป็นไอคอนปฏิทิน **ห้ามซ้อนปุ่มอื่นไว้ใน trigger** ถ้าล้างค่าได้ ให้วางปุ่ม "ล้างวันที่" ไว้ท้าย popover
- เนื้อหาเป็น `Popover` + `Calendar` (`mode="single"`, `weekStartsOn={1}`, `today`, `startMonth`/`endMonth`) แปลง civil `min`/`max` เป็น `Date` แล้วสร้าง matcher `{ before: minDate }` และ `{ after: maxDate }` แยกกันเฉพาะขอบเขตที่มีค่า ทดสอบ min-only, max-only, ทั้งคู่ และวันตรงขอบเขต ภาษาไทยใช้ `react-day-picker/buddhist` + `numerals="latn"`
- Adapter แปลงวันที่ civil ↔ `Date` อยู่ใน `src/lib/format/civilDate.ts` ใช้เวลาเที่ยงตามเวลาท้องถิ่น (`new Date(y, m-1, d, 12)`) และ serialize ด้วย `getFullYear/getMonth/getDate` **ห้ามใช้ `toISOString()` หรือ `Date.parse("YYYY-MM-DD")`** (สองวิธีนี้ตีความหรือ serialize เป็น UTC)
- เมื่อ `disabled`/locked: ไม่เปิด popover และถ้าเปิดค้างอยู่ให้ปิด เมื่อเลือกวันแล้ว popover ปิดและ focus กลับไปที่ trigger

**`MonthField` (ใหม่)**: `value: "" | "YYYY-MM"`, `min?`, `max`, `label` ประกอบจาก `SelectControl` สองตัว (เดือน, ปี) ใน `fieldset`/legend ปีแสดงเป็น พ.ศ. ในภาษาไทย แต่ค่าที่เก็บเป็น ค.ศ. เหมือน `HolidaysScreen` ห้ามเพิ่มขอบเขตย้อนหลังที่ไม่มีใน contract เดิม; ถ้ารายการปีโหลดเป็นช่วง ต้องเลือกปีปัจจุบันของค่าและขยายไปยังปีก่อนหน้าได้จนถึง `min` จริงของ caller

**`TimeField` (ใหม่ เป็น composition)**: `value: "" | "HH:mm"`, `onValueChange`, `label`, `required?`, `clearable?`, `disabled?`, `invalid?`, `describedBy?` ใช้ field trigger พร้อมไอคอนนาฬิกาและ `Popover` ตาม preview ภายในมี `SelectControl` ชั่วโมง (00–23) และนาที (00–59) ใน `role="group"` ที่มี `aria-labelledby` ชี้ label; แต่ละ Select มีชื่อ "ชั่วโมง"/"นาที" เก็บค่าที่กำลังเลือกใน popup และ commit เมื่อกด "เสร็จ" เท่านั้น ถ้าเลือกไม่ครบปุ่มนี้ disabled; Escape/คลิกนอก popup ยกเลิกเฉพาะค่าที่ยังไม่ commit และไม่แตะค่าของ caller เปิดครั้งถัดไปเริ่มจากค่าของ caller; ค่าว่างไม่เติมเวลาเริ่มต้นโดยเงียบ ๆ ล้างเวลาได้เมื่อ caller อนุญาต การเปลี่ยนเป็น disabled/locked ปิดและทิ้ง popup draft การ commit ที่ผู้ใช้ทำจริงต้องส่ง event แม้ `HH:mm` เท่าค่าเดิม เพื่อให้ `TimeSideField` ตั้ง `untouched: false` และรักษา minute-precision contract ได้ shared UI ไม่ import จาก `features/hr`; การตรวจเชิง domain ยังใช้ `parseTimeInput`/`parseLocalTime` ที่ caller เดิม

**Validation หลังเลิกใช้ native picker:** trigger แบบปุ่มไม่มี browser `required`/`min`/`max` validation อัตโนมัติ ต้องผูก field error กับ validation ของ caller และพิสูจน์ว่าค่าว่างหรือค่านอกช่วงยัง submit ไม่ได้ ห้ามถือว่าใส่ `required` บน trigger แล้วเพียงพอ

**`TimeSideField`**: คง `TimeSide { value, nextDay, untouched? }`, `toLocalTimeInput`, `sideFromInstant` และพฤติกรรม `untouched: false` ทุกครั้งที่ผู้ใช้แก้ไขจริง ต้องรักษา SOL-02 ใน system audit: re-review ห้ามปัดเวลาที่ไม่ได้แตะ

**i18n**: เพิ่ม key ใหม่ (ชื่อปุ่มเลือกวันที่, ล้างวันที่, เดือนก่อน/ถัดไป, ชั่วโมง, นาที, เวลาไม่ครบ) ทั้งใน `messages/th.json` และ `messages/en.json` และตรวจ parity ด้วย `src/i18n/messages.test.ts` ที่มีอยู่

## 12. การตรวจที่ต้องทำจริง (accessibility, keyboard, portal, จอเล็ก)

- Keyboard: Tab ผ่าน field และ in-field action; Select ใช้ลูกศร/Enter/Escape/typeahead (พิมพ์ "3","0" ได้นาที 30); ปฏิทินตามข้อ DS-5; Escape ปิดชั้นบนสุดก่อน แล้ว focus กลับไปที่ trigger
- Focus: มองเห็นได้ทั้ง light และ dark; focus ที่ invalid เห็นขอบเดียวที่ชัด; inset focus ของ in-field action ต้องไม่ถูกตัด
- Portal/scroll: Select และ Popover อยู่ใน Dialog, Sheet และ `TableScroller`; เนื้อหายาวเลื่อนได้; ไม่หลุดออกนอก viewport ที่ 320px; มีการตรวจ `prefers-reduced-motion`
- Contrast: ข้อความและ placeholder ≥ 4.5:1; ขอบ, focus และไอคอนที่มีความหมาย ≥ 3:1; badge ≥ 7:1 (มี test อยู่แล้ว)
- Zoom 200% ที่ 1440 และ Thai wrapping
- สิ่งที่ harness พิสูจน์ไม่ได้: screen reader จริง, อุปกรณ์สัมผัสจริง (Radix Select บน touch อาจมีปัญหา click-through), กล้อง และ Clerk ใน production ต้องรายงานแยกและห้ามอ้างว่าผ่าน

## 15. Tradeoff และคำถามที่ยังเปิดอยู่

**Tradeoff ที่ตั้งใจรับตามทิศทางของผู้ใช้ (ไม่ย้อนคำสั่ง)**

- Field สัมผัสสูง 40px ต่ำกว่าปุ่มของ app ที่ 48px ส่วน in-field action บนจอสัมผัสมีพื้นที่ประมาณ 38×38px (หักขอบแล้ว) ต้องวัด hit target และระยะห่างจริง โดยเฉพาะ scan + trailing ที่อยู่ติดกัน ขนาดที่ตั้งไว้เพียงอย่างเดียวยังไม่ใช่หลักฐานรับรอง accessibility
- Field ใน dense สูง 32px แต่ปุ่มข้าง ๆ สูง 36px ทำให้ toolbar ไม่เสมอกัน จะจัดแถวด้วย `items-end` และไม่ลดขนาดปุ่ม

**คำถามที่ยังเปิดอยู่ (ไม่บล็อกการเริ่ม DS-0 ถึง DS-5)**

1. ปุ่มที่อยู่คู่กับ field (เช่นแถวค้นหาของ catalogue) ควรสูงเท่า field แบบที่ `review.css` ทำใน sheet (`.catalogue-search > .btn`) หรือคง 36/48? ค่าเริ่มต้นของแผนคือคง 36/48 เพื่อรักษา target บนจอสัมผัส
2. `MonthField` ต้องรักษาช่วงประวัติที่เข้าถึงได้เดิม ใช้ `min`/`max` ของ caller เท่านั้น; รายการปีจะแบ่งโหลดเป็นช่วงได้ แต่ต้องขยายย้อนหลังได้ และห้ามตั้งขอบเขต 10 ปีขึ้นเอง
3. ปุ่ม scan/AI ของ `LocationPicker` ควรย้ายเข้ามาในช่อง field หรือไม่: ค่าเริ่มต้นคือคงไว้ข้าง field เพราะมีสอง action และมีปัญหาซ้ำซ้อน (R21/R22) ที่ยังรอตัดสินใจ
4. `type="color"` ใน `AreaColorPicker` และ `type="range"` ใน `BarcodeCropControls` ควรเปลี่ยนเป็น Radix/shadcn ด้วยหรือไม่: ค่าเริ่มต้นคือคง native เพราะไม่อยู่ในรายการ picker ที่ผู้ใช้สั่ง

## 16. เงื่อนไขการ release และ rollback

- **แผนนี้ไม่อนุมัติ production release** การ merge เข้า `main` จะ release production อัตโนมัติหลัง `Planner quality` ผ่าน ทุก slice จึงต้องได้รับอนุญาตจากผู้ใช้อย่างชัดเจนก่อน merge
- ก่อนขออนุมัติ: PR ผ่าน `check`, CodeQL, harness และการตรวจ browser แบบ authenticated บน staging ตาม pipeline; ห้ามใช้ `vercel --prod`, deploy hook หรือ Redeploy
- Rollback: ใช้ PR ที่ revert slice ผ่าน pipeline เดิม ทุก slice เป็น frontend-only และไม่มีการเปลี่ยน Convex จึงใช้ `vercel rollback` ได้ตาม runbook เมื่อ artifact เข้ากันได้กับ backend ปัจจุบัน ไม่มีข้อมูลต้อง migrate
- เงื่อนไขที่ต้องหยุดหรือ revert: action ของ domain หายไป, permission boundary เปลี่ยน, keyboard หรือ focus ถดถอย, ค่าที่ส่ง server ต่างจากเดิม หรือ Back inventory ต้องใช้ exemption

## 17. สิ่งที่ทำและไม่ได้ทำในการวางแผนครั้งนี้

ทำ: อ่านเอกสารและ source ข้างต้นแบบ read-only; นับด้วย `grep`/`find`/`node` บน working tree ปัจจุบัน (ตัวเลขอาจเปลี่ยนเพราะ agent อื่นยังแก้อยู่); ตรวจ `react-day-picker` export `buddhist` และค่าเริ่มต้น `numerals: thai` จาก `.d.ts`; ดึงชื่อเคส test จากไฟล์ที่มีอยู่

ไม่ได้ทำ: รัน test, build, lint, harness หรือ browser; ติดตั้งหรือย้าย dependency; แก้ไฟล์อื่นนอกจากไฟล์นี้ ไม่ได้ยืนยันว่า Playwright emulate `pointer: coarse` ได้, ไม่ได้ยืนยันพฤติกรรมการ scroll ของ Popover ใน Dialog แบบ modal และไม่ได้ยืนยันผลลัพธ์จริงของ shadcn CLI
