## Design decisions and constraints

1. Keep one shell owner and the existing public seams: `useNavigationDraft`, `requestTransition`, `settle`, and the `lib/navigationGuard` bridge. Feature adapters continue owning business outcomes and draft disposal.
2. **Revise the original one-buffer mechanism for N1.** Creating a synthetic history entry when a draft becomes dirty cannot preserve an existing Forward branch. Renaming markers, adding cleanup or using a timer cannot fix that destructive push. No final replacement is claimed proven yet.
3. Preferred candidate for the bounded prototype: feature-detected Navigation API entry keys and traverse events, with no synthetic dirty-entry push on the path being fixed. Inspect actual event capabilities: cancel before commit only when `event.cancelable` permits it; otherwise prove same-document restoration by entry key before Next consumes the destination's `popstate`. After restoration, show one prompt and replay the exact destination on approval with a bounded approval token. Clear that token on completion, cancellation, superseding navigation or owner teardown. Test `traverseTo()` rejection and missing/disposed entries. The installed Next router remains responsible for rendering; do not substitute a custom router. Committed app depth is not physical browser distance, especially around old buffers and native fragments. Never derive unknown direction from `history.length` or guess a one-step delta.
4. Same-page query replacement must retain or refresh ownership of an unchanged legacy guard marker. Clear that ownership when the marker, entry or route is genuinely left. An unexpected write during restoration/removal must still invalidate the superseded traversal.
5. Treat old `__storageWorkspaceGuard` entries as a compatibility concern across reloads and deployments. Pages cannot delete arbitrary browser history entries. Compatibility handling may replace the current entry or skip an obsolete duplicate during traversal, without recreating Forward loss or accumulating new buffers.
6. Internal restoration/removal stays invisible to Next route progress and committed-query readers. Preserve Next router state, catalogue markers, locale, unrelated query and hash values. Do not synthesize fake Next router trees or dispatch fabricated browser events to trick the router.
7. Pending writes block leaving and discarding. Keep editing retains all drafts. Save failure retains data. Save-and-continue requires the sole saveable draft and must recheck pending/dirty registrations before proceeding. Disposal and approved navigation happen exactly once.
8. Keep the guard's internal representation private and derive it from the proven mechanism. A discriminated traversal state must delete invalid combinations and reset duplication, rather than add a parallel abstraction. If the new mechanism has no buffers, retain a private `Buffer` record only where legacy compatibility requires it. No new state-machine dependency, generic mutation framework, payload cache or cross-account mutable data store.
9. HR ID cleanup must distinguish an obsolete owner with no successor from a newer owner actively recovering the same ID. Equality of the request ID alone does not establish ownership. Keep exact uncertain command retries, scalar session formats, organization/actor isolation and clock-only durable recovery unchanged.
10. Read `AGENTS.md` and installed Next.js 16.3.8 guides before implementation, especially `01-app/01-getting-started/04-linking-and-navigating.md` and `01-app/03-api-reference/04-functions/use-router.md`. Inspect the installed router's history behavior rather than relying on older Next assumptions.

The prototype must compare the key-based candidate with Kiro's smaller hybrid: retain the existing buffer outside the supported Forward path and use entry-key traversal when a Forward entry is exposed. This is a candidate, not a decision to ship two permanent mechanisms. A missing Navigation API does not mean Forward history is empty; `canGoForward === false` must not be treated as proof that no cross-origin browser history exists. Current [MDN guidance](https://developer.mozilla.org/en-US/docs/Web/API/Navigation_API) documents both same-origin entry exposure and unavailable traverse cancellation: treat non-cancelable traversal as the primary case to prove, not a rare fallback. Record the actual feature/entry scope and browser support. If a fallback still truncates history, N1 remains open for that fallback and any eventual PR must state that limited scope. Prefer the smallest proven mechanism; if safe support cannot be demonstrated, retain current guard behavior with its known limitation and ship only the independent N2/unload fixes.

## Delivery sequence

### A. Focused regression fixes and a browser design gate

1. **Establish behavior tests.** Reuse the existing guard/provider and workspace test infrastructure. Add N2 tests for changing view both before and after reload, remount/StrictMode, marker replacement, real route departure, and superseding writes. Add N1 tests with real queued Back/Forward, a clean control, Keep editing, discard, successful/failed save, pending state and rapid repeated traversal. Retain the expected-failing N1 cases on the prototype branch until its fix is ready; do not merge a red suite or mark the gap solved by skipping its assertions.
2. **Fix N2 narrowly.** Reconcile orphan ownership for same-entry query replacements. Preserve existing cancellation of overtaken removal/restoration. Verify the actual Floor `useFloorWorkspaceView` adapter and a real Next page, not only a handcrafted history object.
3. **Make unload protection conditional.** Attach/remove `beforeunload` synchronously with the owner's dirty-or-pending registrations and connect/disconnect lifecycle; remove it after the last protected entry settles or unregisters. Reuse the conditional pattern already present in `useUnsavedWarning`, while preserving the owner's synchronous registration semantics. Check clean → dirty → clean, pending-only, multiple registrations and owner remount. Verify native reload/leave confirmation when protection is active after a real user gesture; separately document the browser restriction before activation. Check Firefox document-cache eligibility separately from SPA routing; other browser/cache blockers may remain.
4. **Prototype N1 through the real provider seam.** First prove the candidate in an isolated browser experiment; then use the installed Next router and app shell. Reuse the existing browser harness where possible. The prototype must exercise an existing Forward branch without adding any synthetic dirty-entry push. Limit the first spike to one focused implementation/review cycle: its output is the browser matrix, chosen mechanism and go/no-go report, not an indefinitely expanding rewrite. A no-go closes this cycle with N1 unresolved and a concrete explanation.

The N1 gate must record the exact policy and measured result for every row before a replacement guard is approved:

| Situation                                                        | Required result / decision                                                                                                                                                                                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Known app Back, Forward and multi-entry `history.go()`           | Restore on cancellation and replay the exact destination on approval; preserve all existing Forward destinations.                                                                                                                   |
| Direct-open page and unknown/pre-tracker entries                 | Demonstrate a safe explicit policy without a guessed history delta, infinite bounce or draft loss. If impossible with the candidate, reject it and document the supported alternative before production changes.                    |
| Native hash/skip-link entries, query pushes and replacements     | Keep fragment accessibility and committed URL readers correct; no stuck route loading or phantom Back steps.                                                                                                                        |
| Legacy same-URL buffers, reload and StrictMode                   | No added duplicate entries; first real Back reaches the preceding committed page; old metadata stays compatible.                                                                                                                    |
| Cross-document or external destination                           | Preserve native unload protection; do not claim SPA interception can universally cancel these traversals.                                                                                                                           |
| Rapid Back/Forward, pending save, another draft registers        | One prompt and at most one permitted action; no loss of newly dirty/pending work; no timeout synchronization.                                                                                                                       |
| Next router refresh, redirect, query change and superseding Link | Router tree and application metadata remain valid; cancelled traversal does not expose a destination or leave progress stuck.                                                                                                       |
| Null-state hash entry vs non-null state lacking `__NA`           | Demonstrate distinct handling. Installed Next ignores the former but reloads for the latter; cancelled/internal recovery must not leak an unmarked entry to Next, and approved document transitions must be explicit.               |
| Browser toolbar/menu Back and activation                         | Test Back-menu jumps, rapid repeated Back, and a draft restored on mount before a fresh user gesture. Record a real browser-control or manual device check; script `history.back()` alone cannot establish entry-skipping behavior. |
| Navigation API absent, partial, or entry unavailable             | Feature detection and explicit fallback coverage; no false claim that absent APIs or an empty exposed entry list mean no physical Forward branch. Test cancellation capability and failed/disposed `traverseTo()` targets.          |
| Chromium, Firefox and WebKit                                     | Run supported browser engines; record any unavailable runner or browser-specific limitation explicitly. Chromium alone is not a cross-browser pass.                                                                                 |

Go means every row meets its required result for each browser/feature scope being claimed fixed. A partial go must list supported engines and retain behavior no weaker than the current guard elsewhere, leaving N1 open for every unfixed scope. If the N1 gate fails, the small N2/unload fixes can ship independently after their own checks, while N1 remains explicitly open. Do not expand into an unbounded navigation framework or accept silent loss of Forward/draft protection as the fallback. The prototype is an implementation entry task, not evidence that a replacement already works.

### B. Implement the proven navigation mechanism and reduce duplication

5. **Replace only the proven guard internals.** After the gate passes, revise the private guard representation and handle legacy buffers. If the new mechanism no longer creates buffers, retain the N2 reconciliation only for legacy entries and remove obsolete active-buffer paths when compatibility evidence permits. Preserve the caller interface and already-shared URL/lifecycle modules. Keep state-representation-only changes separate from behavior changes where that makes review safer; avoid a rewrite merely to reduce line count.
6. **Consolidate the actual subscription duplication.** Export one history-write-plus-popstate subscription used by `PageBackButton` and `HrShared`. Do not introduce a new global React context or merge their different snapshot values. Verify cleanup/remount and HR authorized direct-open fallback behavior. This is maintenance work; no measurable speedup is promised.
7. **Independent audit and integration verification.** Sol 6.1 reviews the final diff against requirements and tests; Kiro reviews frontend integration. Root resolves concrete disagreements with source evidence and a regression, then runs the acceptance matrix below.

### C. Separate conditional follow-ups

8. **HR request ownership (W1).** First reproduce a real same-intent remount through an auth/access transition or document the supported recovery contract requiring this lifecycle. If accepted, add public-hook races: old definite completion with no successor; successor already recovering the same ID; old completion after a successor's uncertain result; changed scope A → B → A; denied/refused/uncertain outcomes; unavailable storage. The candidate is a tab-local latest-sender token keyed by the existing organization/actor/intent scope, claimed at send time. A definite result may clear its ID only if its sender still owns the claim; an obsolete component with no newer sender can therefore clean up. Test this protocol before implementing it in the existing request-identity seam; ID comparison alone is insufficient. Any extra ownership state stores identifiers only, has explicit cleanup/lifetime rules, and cannot erase a successor's retry. No backend idempotency or payload-persistence redesign.
9. **Manual error setter (H1).** Defer unless a production callback can retain it across scope/lifetime changes. If such a caller is found, bind the callback to its originating lifetime and add that caller's regression; do not broaden every synchronous setter by default.
10. **Investigate reported 10-second navigation.** Capture representative production-mode traces for click → route commit → data ready, with cache/network state and route pairs. Separate OCR, backend queries and hydration from guard traversal. Compare like-for-like repeated samples and report p50/p95 only with sample counts. Reuse existing observability first; redact query/payload/identity data. Propose a performance change only once a bottleneck is measured. Do not run heavyweight build/test jobs concurrently with timing measurements.
