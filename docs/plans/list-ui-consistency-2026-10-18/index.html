Search → Filter ในแถวเดียวกัน

ใช้ CollectionToolbar เดิมเป็นฐาน ช่องค้นหาขยายตามพื้นที่และปุ่ม filter อยู่ถัดทางขวาเสมอ ลดการวาง controls เฉพาะหน้าที่ทำให้แต่ละหน้าดูต่างกัน

Component และ interaction กลาง

  • ปรับ toolbar ให้ search มี min-width: 0 และปุ่มมีขนาดคงที่ ป้องกันการตกลงอีกบรรทัดบนจอแคบ

  • ตัวกรองสถานะแบบเลือกหนึ่งค่าใช้ radio พร้อมข้อความเต็ม ไม่ให้ผู้ใช้เดาความหมายไอคอน
  • ตัวกรองหลายเงื่อนไขใช้ shared Sheet เดิม พร้อม Apply / Reset / Cancel และ draft ที่แยกจากค่าที่ใช้จริง
  • ใช้ surface แบบ Back-aware เดียวกันทั้ง Mobile/Desktop โดยความกว้าง panel ปรับตามจอ

การเชื่อมกับข้อมูลและ workflow

  • เปลี่ยนสถานะ คำค้น หรือ sort → reset หน้าแรกและ selection ที่ผูกกับหน้าปัจจุบัน
  • หน้าใบงานคงค่าเริ่มต้น UNMAPPED และการ debounce search เดิม
  • รักษา query / locale / hash และ selected-detail behavior ของหน้าที่มี deep link เช่น HR Review
  • ปิด filter ต้องคืน focus ให้ปุ่มเปิด; pending write ป้องกันการเปลี่ยนข้อมูลตาม contract เดิม

ขอบเขตความรับผิดชอบ

PaginationFooter ไม่ fetch ข้อมูล ไม่รู้จัก Convex/table type และไม่เก็บ state ของแต่ละหน้า ส่วน adapters แปลง state เป็น props; controller รับผิดชอบ cursor หรือ page index; feature รับผิดชอบ query และ business rules จึงใช้ footer เดียวได้กับทั้งตาราง การ์ด และรายการเลือกตำแหน่ง

State ของแต่ละรายการแยกด้วย org / actor / warehouse / list ID / criteria การใช้ component กลางจึงไม่ทำให้หน้า Batch, หน้า HR หรือข้อมูลคนละคลังใช้ page/cursor ปะปนกัน

Controlled API ที่เสนอสำหรับ component กลาง

นี่เป็น contract ในแผน ยังไม่ใช่ API ที่แก้ลง production จะรักษา compatibility ระหว่างทยอยย้าย caller แล้วลบ props เก่าหลังย้ายครบ 

type PageSize = 20 | 50 | 100;

type PaginationStatus =
  | { kind: "known"; from: number; to: number; total: number }
  | { kind: "cursor"; page: number; itemCount: number };

type PaginationAction = {
  enabled: boolean;
  onSelect: () => void;
};

type PaginationFooterProps = {
  label: string;
  pageSize: PageSize;
  onPageSizeChange: (size: PageSize) => void;
  status: PaginationStatus;
  actions: {
    first: PaginationAction;
    previous: PaginationAction;
    next: PaginationAction;
    last: PaginationAction;
  };
  loading?: boolean;
  disabled?: boolean;
};

งาน backend ที่ต้องทำให้ครบก่อนเปิดความสามารถทั้งหมด

Cursor APIs ปัจจุบันส่ง continueCursor และ isDone แต่ไม่มี total/last cursor การทำปุ่มหน้าสุดท้ายจริงต้องเพิ่ม query contract ที่รองรับการเริ่มจากท้ายด้วยลำดับคงที่ และ exact aggregate ที่มีขอบเขตสิทธิ์ตรงกัน งานนี้เป็น dependency ของการเปิดใช้ Last และยอดรวมบนหน้ากลุ่ม cursor ไม่แก้ด้วยการโหลดทั้งฐานข้อมูลเข้า browser
รายละเอียดการเพิ่ม total และ Last ให้ cursor APIs
  1. กำหนดลำดับที่เสถียร: sort key ตามด้วย unique ID และ bind cursor กับ org / warehouse / actor / criteria / sort / page size
  2. เพิ่ม response capability เช่น totalItems?: number, range?: { from; to }, firstCursor, lastCursor, previousCursor โดยใช้รูปแบบ cursor ที่ตรวจสอบจาก server
  3. ทำ exact aggregate ที่ตรงกับ filter จริง ใช้ indexed query / maintained aggregate ตามชนิดข้อมูล ทบทวนต้นทุนสำหรับ full-text และ multi-filter ก่อนเลือกวิธี
  4. การไป Last ต้องดึงหน้าสุดท้ายที่มีสมาชิกและลำดับตรงกับการกด Next จากต้นทาง รวมกรณีจำนวนหาร page size ไม่ลงตัว; ต้องย้อนกลับได้โดยไม่พึ่งประวัติที่ยังไม่เคยโหลด
  5. เพิ่ม pageSize=100 ให้ endpoint ที่ยังจำกัด 50 หลังทบทวน query budget เช่น HR requests; UI ไม่ส่ง size ที่ server ยังไม่รับ
  6. live insert/delete อาจทำให้ range ขยับ: invalidate position หรือคืน cursorReset ตาม scope และแสดงผลใหม่ หลีกเลี่ยงยอด range กับ rows ที่มาจากคนละ criteria/revision
  7. เพิ่ม APIs สำหรับพนักงานและงวดงานที่แบ่งหน้าจริง รักษา endpoint เดิมถ้ายังมี consumers สำหรับ editor/options; warning complete=false ยังคงอยู่จนมี continuation ครบ

หาก exact total ของบาง filter ยังมีต้นทุนไม่เหมาะสม จะแสดงสถานะแบบ cursor ให้ชัดและคงข้อจำกัดนี้เป็นรายการค้างก่อนประกาศว่าได้รูปแบบ ReUI-12 ครบทุก capability

ครอบคลุมหน้าไหนบ้าง

สำรวจ production table และ mobile counterpart จาก source แล้ว ตารางต่อไปนี้ระบุว่าต้องย้ายการแสดงผล เพิ่ม controller หรือเพิ่ม API จริง รวมทั้งรายการแบบการ์ดที่ผู้ใช้เห็นแทน table บนมือถือ

ลำดับ implementation

ทำส่วนกลางให้พร้อมก่อนย้าย caller และเพิ่ม capability backend ให้ครบก่อนเปิดปุ่มที่ต้องอาศัยข้อมูลนั้น แต่ละช่วงมีผลลัพธ์และหลักฐานตรวจรับชัดเจน

  1. Foundation

    กำหนด contract และพฤติกรรมกลาง

    สรุป API ของ PaginationFooter, ขนาดหน้า, ข้อความ TH/EN, capability known/cursor และ toolbar layout; อ่าน Next.js docs ของเวอร์ชันใน node_modules ก่อนแก้ runtime

    ผ่านเมื่อ: shared footer ทำงานกับ known / cursor / empty / loading ได้โดยไม่ผูกกับ feature
  2. Global controls

    สร้างส่วนกลางแล้วพิสูจน์กับหน้าใบงาน

    ปรับ Footer/PageSizeSelect, เพิ่ม local adapter/hook, สร้าง filter button และย้าย JobScanRecords เป็น caller แรก; ตรวจ search, filter, selection และ Location workflow

    ผ่านเมื่อ: Mobile/Desktop เห็นชุด controls เดียวกัน และกดเปลี่ยนหน้า/กรองแล้ว target ไม่ผิด
  3. Data capability

    เพิ่ม pagination จริงให้ API ที่ยังขาด

    ทำ paged Employees/Periods และ total/end-cursor capability สำหรับ cursor endpoints ตาม query/index ที่ใช้จริง; ตรวจ permission, sort stability, query budget และ live invalidation

    ผ่านเมื่อ: เข้าถึงข้อมูลเกินขอบเขตเดิมได้ และ Last / Previous ตรงกับลำดับผลลัพธ์จริง
  4. Caller migration

    ย้ายครบตาม inventory

    อัปเดต cursor callers เดิม, เพิ่ม local pagination ให้ตารางที่ยังไม่มี, ลบ footer เฉพาะหน้า; จัด page description และ metadata แยกตามความหมาย พร้อมมาตรฐาน filter

    ผ่านเมื่อ: ตรวจ production callsites ครบ ทุกตารางรายการอ้างอิง footer กลาง และ cards ใช้ page เดียวกับ table
  5. Navigation + QA

    ทดสอบ workflow และเก็บ screenshots

    ทบทวน navigation inventory เฉพาะ state/semantic targets ที่เปลี่ยน; รัน unit/integration/caller navigation, typecheck, ESLint และ navigation gate; ตรวจ browser แบบ batched Mobile/Desktop แล้วแก้ที่พบพร้อมกัน

    ส่งมอบ: screenshots จากแอปจริง 390px และ 1440px, filter เปิด/ปิด, page แรก/ถัดไป, empty/loading และบันทึกข้อจำกัดที่ยังมี

เกณฑ์ตรวจรับก่อนเรียกว่าเสร็จ

UI และ component กลาง

  • ไม่มีคำอธิบายหน้าใต้ header ที่อยู่ในขอบเขต และข้อมูลจริงที่ย้ายออกจาก summary ยังหาเจอ
  • Search/filter อยู่แถวเดียวที่ 320, 390, 768 และ 1440px; ไม่มี horizontal overflow ของหน้า
  • ทุก list/table ใช้ footer renderer เดียว ไม่มี markup ชุดปุ่ม pagination เฉพาะหน้าเหลือโดยไม่มีเหตุผลที่ตรวจแล้ว
  • ทดสอบ 0 / 1 / 20 / 21 / 50 / 100 / 101 รายการ, disabled, loading และปุ่มไม่ submit form
  • Keyboard, focus return, accessible names, TH/EN และ light/dark ใช้งานได้ครบ

ข้อมูลและ navigation

  • ผล filter/search/sort ถูกแบ่งหน้าหลังประมวลผลครบ และ Last ไม่ข้าม/ซ้ำข้อมูลจากลำดับที่กำหนด
  • พนักงานเกิน 99 ต่อไซต์และงวดเกิน 200 ยังเปิดได้จริง ไม่ใช่ client pagination บนข้อมูลที่ถูกตัด
  • ลบแถวสุดท้ายของหน้า, live removal และ cursor reset ไม่ค้างในหน้าว่างที่ออกไม่ได้
  • ยอดรวม/CSV/save payload ไม่ลดเหลือเฉพาะหน้าปัจจุบัน; pending และ dirty drafts ได้รับการป้องกัน
  • Back ปิด foreground ก่อน, Close/Cancel แล้ว Back ถัดไปถูกต้อง; detail return, direct link, locale/query/hash, Forward และ refresh ผ่าน caller tests ที่เกี่ยวข้อง
