# Global search + AI navigation: research

วันที่ตรวจสอบ: **9 ตุลาคม 2026** · ขอบเขต: หลักฐานเพื่อวางแผน ยังไม่ได้เพิ่มฟีเจอร์หรือทดสอบ AI endpoint จริง

เอกสารนี้บันทึก research ก่อน implementation; ผลตรวจฟีเจอร์และโมเดลที่ทำภายหลังอยู่ใน [Independent validation](../reviews/global-search-independent-validation-2026-10-09.md)

ข้อเสนอจากงานวิจัยนี้คือใช้ **สัญญาปลายทางเดียวกัน** สำหรับ search ปกติและ AI: ระบุหน้า → ส่วนย่อย → รายการที่มีสิทธิ์เข้าถึง → ช่องที่ต้องแก้ ระบบสร้างลิงก์จากข้อมูลที่ตรวจแล้ว ส่วน AI ช่วยตีความความต้องการของผู้ใช้ แนวทางนี้เป็นข้อเสนอของโครงการ ไม่ใช่ข้อกำหนดของผู้ให้บริการ

## สิ่งที่พบในโครงการ

- [package.json](../../package.json) ใช้ Next 16.3.8, Convex 1.46.0, React 19.2.8 และ Radix UI; ไม่มี AI SDK ใน dependencies
- มี OpenRouter integration อยู่แล้วใน [extractJobTicket](../../convex/finishedGoods/jobScans.ts): server-side `actionWithOrg`, `response_format: json_schema`, `strict: true` และ parse ผลด้วย `parseJobTicket` การใช้เส้นทางนี้เป็นทางเลือกที่เข้ากับโครงการ แต่ยังไม่ยืนยัน credential, endpoint capability หรือความเหมาะสมของโมเดลกับภาษาไทย
- [TenantActionFunctionContext](../../convex/lib/tenantFunctions.ts) เปิดให้ใช้ identity/tenant/permission แต่ไม่มี DB หรือ `runQuery`; แผนจึงใช้ AI action แปล intent แล้วให้ domain query resolvers ที่มีสิทธิ์เดิมค้นรายการ ไม่สมมติว่า action wrapper ค้น records ได้เอง
- อ่านคู่มือ Next ที่ติดตั้งใน `node_modules/next/dist/docs/` สำหรับ `use-router`, `use-search-params` และ `Link` ด้วย เพราะเอกสารเว็บล่าสุดแสดง 16.4.0 ซึ่งใหม่กว่าเวอร์ชันโครงการ

## คำแนะนำสำหรับแผนของโครงการ

1. **สร้างฐาน navigation ก่อน:** index ชื่อหน้า คำอธิบาย alias ไทย/อังกฤษ และส่วนย่อยที่เข้าถึงได้จาก registry กลาง ผลลัพธ์แสดง breadcrumb เช่น “บุคลากร › พนักงาน › ตารางทำงาน” และชื่อปลายทางที่ชัดเจน ค้นเมนูได้โดยไม่เรียก AI
2. **ทำ durable deep link ให้ปลายทาง:** หน้าที่ใช้ React selection state ต้องมี URL contract สำหรับ tab/รายการ/วันที่/section เมื่อเปิดจาก search, reload หรือ Back ต้องกลับสู่รายการเดิมได้ ตรวจข้อมูลและสิทธิ์ก่อนเปิด editor และไม่ทำ save ผ่าน URL
3. **เพิ่ม entity เป็นรายกลุ่ม:** เริ่ม exact ID/code และชื่อที่ได้รับอนุญาตใน HR ตามขอบเขตจริง จากนั้นทดลอง Thai token field บน corpus ที่มีคำติดกัน ชื่อยาวเกิน 32 ตัวอักษร ไทย/อังกฤษ mixed และรหัสมีขีด คง raw display text ไว้; หาก recall ไม่ผ่านจึงเปรียบเทียบ engine อื่น แทนการ scan ทุก table ทุก keystroke
4. **ปุ่ม AI ใช้ปลายทางชุดเดียวกัน:** รับข้อความเช่น “แก้เวลางานของ EMP-001 วันที่ 8 ต.ค.” → AI แปลเป็น intent → ตรวจ schema/allowlist → domain queries หา authorized candidates → app สร้าง typed destination การเรียก AI นี้ส่งคำถามและ metadata ของ route/section โดยไม่ส่ง HR record sets ไปให้ provider ถ้ารหัส exact/วันที่ของตนเองครบและ resolve เป็นรายการเดียวจึงพาไปทันที; ถ้าข้อมูลขาดหรือมีหลายรายการ ให้ถาม/เลือก inline ด้วยชื่อ รหัส และวันที่จริง ผล fuzzy อันดับแรกเพียงรายการเดียวหรือการค้นที่ยังไม่ครบไม่ถือเป็นหลักฐานให้ auto navigate
5. **เริ่ม AI ด้วย route/section ได้ก่อน entity corpus ครบ:** สัญญาของโมเดลมี intent/route/section enums และ lookup fields เช่น employee code/date ที่ app ตรวจอีกครั้ง จากนั้น resolver ของ app คืน `destination / clarify / no_match` พร้อม candidate IDs ที่พบจริง URL สร้างโดย app เท่านั้น ไม่ใช้คะแนน confidence จากโมเดลเป็นหลักฐานว่าสิทธิ์หรือปลายทางถูกต้อง
6. **เก็บ UX ของการแก้ไขไว้ในฟอร์มเดิม:** AI พาไปยังจุดแก้และเน้นเป้าหมาย ผู้ใช้แก้/บันทึกตาม validation และ audit เดิม หากรายการถูกลบ สิทธิ์เปลี่ยน หรือ link เก่า ให้แสดงข้อความและปลายทางแม่ที่เข้าถึงได้ Search ปกติต้องใช้ได้เมื่อ AI timeout/unavailable

## สิ่งที่ต้องวัดก่อนเลือก implementation

- Thai segmentation ใช้ได้และให้ token ชุดเดียวกันใน runtime ที่เลือกหรือไม่; ผลต่อ exact name, partial name, compounds และ typo ต้องวัดแยกกัน ไม่มีการ benchmark ใน research นี้
- จำนวน entities และสิทธิ์ของแต่ละ module จะกำหนด index/filter/ranking ที่เหมาะสม Search query ของ Convex return ตาม relevance และมี limit; ตรวจเอกสารกับ deployment รุ่นที่ใช้งานก่อนจัด schema [Convex search behavior](https://docs.convex.dev/search/text-search#search-behavior)
- OpenRouter endpoint ที่กำหนดรองรับ schema จริงหรือไม่, privacy settings, cost, latency และคุณภาพภาษาไทยยังไม่ตรวจ ไม่มี provider/model commitment ในเอกสารนี้
- ต้องทดสอบ keyboard/focus + VoiceOver, ภาษาไทย/อังกฤษ, phone, reload/Back, ลิงก์ที่ไม่มีสิทธิ์ และการเปลี่ยน org รวมถึง authorization แยก employee/team/HR admin
- AI evaluation ควรมีข้อความไทยที่มี expected target, ชื่อซ้ำ, วันที่กำกวม, target ที่ไม่มีอยู่/ถูกลบ, ข้อความสั่งให้ข้ามสิทธิ์ที่ฝังใน record, output ผิด schema, timeout และตรวจว่าไม่มี mutation เกิดจาก navigation

เอกสารนี้ยืนยันข้อจำกัดและแนวทางจากแหล่งทางการเท่านั้น ไม่ยืนยันประสิทธิภาพ คุณภาพ AI หรือความพร้อม credential ของระบบปัจจุบัน
