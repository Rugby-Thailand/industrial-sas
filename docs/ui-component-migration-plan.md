# UI component migration implementation plan

Status: **implemented and verified on 2026-08-12**

This plan closes the gap between the repository's existing UX research and the
current hand-built production UI. It is intentionally limited to component
foundations, the application shells, the dashboard, and the production controls
already present in the application. It must not change warehouse domain rules,
Convex authorization, tenant boundaries, or ledger behavior.

## 1. Outcome

Deliver a consistent shadcn/Radix component layer and use it across the current
application, with ReUI examples supplying the higher-level composition patterns.
The warehouse selector shown on `/th/dashboard` must no longer render as a native
OS menu in desktop browsers.

The resulting UI must preserve:

- Thai and English routing and catalogue parity.
- Keyboard and HID scanner operation.
- The 48 by 48 CSS-pixel handheld target.
- Visible focus, inline validation, and accessible names.
- Existing preview-mode and real-mode behavior.
- Existing server-confirmed state and authorization semantics.

## 2. Required references

- Use the Radix implementation of the shadcn Select component:
  <https://ui.shadcn.com/docs/components/radix/select>
- Use the ReUI application dashboard collection as the dashboard composition
  reference:
  <https://reui.io/blocks/application/dashboard>
- Prefer ReUI Dashboard 1's operations-oriented structure: KPI cards, capacity
  or throughput visualization, and an exception/work queue.
- Follow the repository decisions in
  [`reui-authoring-selection.md`](./reui-authoring-selection.md) and
  [`ux-component-research.md`](./ux-component-research.md).

ReUI application blocks are a visual/composition reference unless the current
environment has a valid Pro entitlement. Do not copy inaccessible premium source.
Use approved free ReUI examples and locally owned shadcn primitives to reproduce
the appropriate structure.

## 3. Current audit baseline

- There is no `components.json` and no installed shadcn/Radix component layer.
- The live dashboard renders two native selects: locale and warehouse.
- Four production renderers use native `<select>`:
  - `src/components/shell/WorkspaceContextBar.tsx`
  - `src/components/shell/LocaleSwitcher.tsx`
  - `src/components/masterData/EntityForm.tsx`
  - `src/features/inbound/ReceiptDetail.tsx`
- Twenty-one production field specifications use `kind: "select"` through the
  shared `EntityForm` seam.
- Production source also contains approximately fifteen locally styled buttons,
  three locally styled inputs, and one textarea.
- The dashboard and shells are composed from local Tailwind markup rather than a
  shared application-component system.
- Existing E2E tests use native-select `selectOption()` calls and there are no
  visual regression screenshots.

## 4. Implementation sequence

### Phase A — shadcn/Radix foundation

1. Initialize shadcn for the existing Next.js/Tailwind v4 project using the
   **Radix** primitive flavor. Do not mix Base UI and Radix implementations.
2. Add and locally own the minimum primitives required by this migration:
   - Select
   - Button
   - Input
   - Textarea
   - Field
   - Card
   - Badge
   - Separator
   - Skeleton
   - Empty
   - Sheet
   - Sidebar, only if its dependency footprint and current Next.js version pass
     the compatibility check
3. Add the conventional `cn()` utility and dependencies generated by shadcn.
4. Map component styling to the repository's semantic tokens in
   `src/app/globals.css`. Do not replace semantic tokens with hard-coded colors.
5. Preserve `min-h-touch`/`min-w-touch` on handheld-interactive controls.
6. Confirm the selected ReUI free examples compile with the chosen Radix flavor.
   Record any compatibility exception in this plan or a short adjacent note.

### Phase B — eliminate native select rendering

Create one production-ready shared Select implementation using the official
shadcn/Radix composition:

```text
Select
├── SelectTrigger
│   └── SelectValue
└── SelectContent
    └── SelectItem
```

Requirements:

- Styled trigger and portalled content in light and dark color schemes.
- `position="popper"` where trigger-edge alignment is preferable.
- Placeholder, disabled, pending, invalid, and empty-option handling.
- Long Thai labels may wrap or expand without clipping critical identifiers.
- Keyboard operation: Tab, Enter/Space, arrows, Home/End, Escape, and typeahead.
- Focus returns to the trigger after closing.
- At least a 48px trigger and 48px item target on handheld routes.
- Form name/value behavior remains compatible with existing submissions.

Migrate, in order:

1. `WorkspaceContextBar` warehouse selector.
2. `LocaleSwitcher` language selector while preserving `router.replace` and
   transition-disabled behavior.
3. The `select` branch in `EntityForm`, thereby migrating every existing
   `kind: "select"` field specification.
4. `LocationChooser` in receipt and handheld receiving flows.

Use ReUI Autocomplete rather than Select when an option set is unbounded or is a
server-backed domain lookup, including future supplier, PO, SKU, lot, LPN, and
large location lists. Do not turn a two-language locale chooser into an
autocomplete.

### Phase C — standardize fields and actions

1. Refactor `EntityForm` to compose shared Field, Input, Textarea, Select, and
   Button primitives.
2. Preserve its current public field-specification API unless a small typed
   extension is necessary. Avoid rewriting all callers.
3. Preserve required-field validation, server-blamed fields, `aria-invalid`,
   `aria-describedby`, reset behavior, and busy fieldset behavior.
4. Replace production raw buttons with shared Button variants where this does
   not weaken semantics:
   - primary
   - secondary
   - outline
   - destructive
   - icon
5. Replace other raw inputs with shared Input only after verifying scan focus,
   input mode, and keyboard-wedge behavior.
6. Keep semantic HTML where it is already the correct primitive. A raw table,
   form, label, or link is not automatically a defect.

### Phase D — shell and dashboard composition

1. Refactor the desktop shell toward the shadcn Sidebar structure while keeping
   one navigation data source, one active-route calculation, permanent
   organization/warehouse context, and mobile Sheet behavior.
2. Keep the handheld shell task-oriented; do not turn it into a compressed
   desktop dashboard.
3. Recompose the dashboard using ReUI Dashboard 1 as the visual hierarchy:
   - Page heading and current warehouse context.
   - KPI/backlog card row using Card/Badge primitives.
   - Receiving-versus-putaway or capacity visualization using the already
     approved ReUI chart examples when available.
   - Existing accessible occupancy table/map or equivalent capacity section.
   - Exception/work queue or direct operational entry area.
   - Setup/system notices below operational content.
4. Keep real WMS metrics and maintained rollups. Do not introduce invented
   revenue, growth, or analytics values.
5. Every chart must retain a textual or tabular equivalent and must not encode
   meaning through color or hover alone.

### Phase E — tables and state components

1. Create consistent loading, empty, error, pending, and blocked treatments from
   shared Skeleton, Empty, Notice/Alert, and Button primitives.
2. Keep the existing semantic tables initially. Adopt ReUI Data Grid only for
   desktop surfaces that actually require filtering, sorting, column visibility,
   or bounded server pagination.
3. Do not add client-side unbounded loading or weaken tenant-scoped Convex reads.
4. Use responsive Sheet/Dialog/Drawer patterns for details and short edit forms
   only where the current route benefits from keeping list context.

### Phase F — tests and regression guards

1. Update component and E2E tests to operate Radix Select through roles,
   keyboard, and pointer interactions instead of `selectOption()`.
2. Add focused tests for:
   - Thai and English warehouse selection.
   - Locale switching without changing the current route.
   - Required and server-invalid form Select states.
   - Disabled/pending Select behavior.
   - Keyboard selection and Escape focus restoration.
   - Receiving location selection on desktop and handheld.
3. Add Playwright screenshots for the dashboard and representative form at:
   - 360px handheld
   - 768px tablet
   - 1280px desktop
   - Thai and English
   - light and dark color schemes
4. Add a narrowly scoped static check preventing new raw production `<select>`
   elements outside an explicitly documented allowlist.
5. Do not forbid all raw buttons or inputs until the scanner and semantic
   exceptions are documented; prefer incremental enforcement.

## 5. Definition of done

- No native production `<select>` remains unless an exception is documented with
  a tested device-specific reason.
- `/th/dashboard` and `/en/dashboard` render themed Select menus with no OS-native
  light dropdown in dark mode.
- All 21 current `kind: "select"` form specifications work through the shared
  Radix Select renderer.
- Existing Thai/English, accessibility, component, integration, and E2E tests
  remain green after their interaction helpers are updated.
- New keyboard and visual tests pass at the required widths and color schemes.
- `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, relevant unit/a11y tests,
  `pnpm test:e2e`, and `pnpm build` pass.
- The dashboard follows the ReUI operations-dashboard hierarchy without adding
  false data or sacrificing the accessible occupancy representation.
- No domain, authorization, tenancy, ledger, or preview/real-mode contract is
  weakened.

## 6. Working rules

- Preserve unrelated user changes, including any existing modification to
  `next-env.d.ts`.
- Implement in reviewable increments, but do not create commits or push unless
  explicitly requested.
- Prefer official shadcn-generated source and the approved ReUI examples over
  ad-hoc reimplementations.
- Review generated registry code before accepting it.
- If a premium ReUI block cannot be accessed, continue using it as a layout
  reference and implement with available primitives; do not block the migration.
- Stop only for a decision that would change domain behavior or require a paid
  entitlement. Otherwise make the smallest safe assumption and continue.
