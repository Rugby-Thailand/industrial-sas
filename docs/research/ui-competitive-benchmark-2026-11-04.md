# UI competitive benchmark for Yongkit screen audits

Date: **2026-11-04 (Asia/Bangkok)**
Status: reference criteria for UI auditors (gpt-6.1-sol and Opus) who score Yongkit screens 1-10. This is not a feature roadmap. A pattern here is a benchmark to check against, not a requirement to build.

## Purpose, method, limits

Purpose: give auditors concrete, checkable patterns from well-regarded products in each Yongkit module, so a score can point at a specific pattern ("no scanned/expected counter per line, see Odoo") instead of a vague taste call.

Method: read official docs, help centers, design systems, first-party changelogs, and first-party app-store listings. Every pattern cites the page that owns the claim. Some official pages block automated fetches, so each source carries a tag:

- **[V]**: fetched directly from the official page.
- **[A]**: read from a Wayback Machine snapshot of the official page, because the live page needs a login or blocks bots (BambooHR help center, Gusto, OpenAI help, Personio help, SAP Fiori, Polaris).
- **[S]**: seen only in a search-engine excerpt of the official page. Lower confidence. Do not score a screen down on an [S] pattern alone.

Limits: no logged-in product access, so nothing here was checked in a live product. Docs describe intended behaviour, and screenshots in docs may be older than the shipping UI. Feedback details (sounds, colours, animation) are rarely documented, so this file only claims the ones a source states. Patterns from third-party blogs, listicles, and customer-run help desks were dropped, which removed Rippling and Zoho Inventory (see "Thin sources").

Yongkit routes below are relative to `src/app/[locale]/(desktop)/`.

### Patterns to steal

- **Scanned/expected counter on every line, plus a done state.** Show `n/N` per ticket or product line, and mark completed lines with a colour **and** an icon or text (Odoo shows `1/2`, `3/3 Units`, and completed lines in green).
- **One instruction line telling the worker what to scan next.** For example "Scan the source location" or "Scan a serial number" (Odoo). The camera view also carries live state prompts: point at the barcode, hold still, move closer, processing (ML Kit showcase).
- **Scan in any order, with the app classifying the code.** The worker should not have to tap a field before scanning. A job ticket and a location label scanned from the same screen land in the right slot (Katana receiving).
- **Unknown codes get an action, not a dead end.** Show a message naming the code, with a next step such as create, link, or rescan (Odoo **Create New Product**, Katana "link it as a supplier code").
- **Manual entry stays reachable when scanning is the main job.** Use an input with a placeholder such as "Enter barcode", the reason shown under it, and OK/Cancel. Make scan the highlighted primary action (SAP Fiori).
- **Location scans verify, they don't just record.** The scanned location is checked against the expected one. Changing the destination is a separate, labelled exception action, and the worker can skip a task (SAP EWM RF).
- **Success feedback the worker can feel and hear.** Beep and vibration on each accepted scan, with an optional confirm-each-scan mode for risky actions (Sortly).
- **Quantity editing without the keyboard.** Offer `+1`/`-1`, a number pad, and a fill-to-expected button. A repeated scan increments the count (Odoo, Katana).

### Patterns to avoid

- **One field per page across 5-10 pages** (NetSuite WMS receiving). Every page change costs a tap and a reload on a phone. Photo-based ticket scans need retries, so keep the running list and the scan target on one screen.
- **Printed command barcodes as the main control** (Odoo `VALIDATE`, `PUT IN PACK` sheets; Katana commands sheet). These suit handheld laser scanners. Phone-camera workers need on-screen buttons.
- **Icon-only primary scan button** (SAP Fiori "do not show a text"). Yongkit's main scan action should carry a Thai/English label as well as the icon. Workers are new to the app and gloves make mis-taps costly. This deliberately deviates from Fiori.
- **A confirmation pop-up after every scan as the default** (Sortly's **Confirm All Updates**). It doubles the taps per ticket. Keep confirmation for destructive or ambiguous scans only.

### Patterns to steal

- **The full location path appears wherever a location does**, as building › floor › zone › spot. This applies in search results, on pallet and batch detail, and in move history (Odoo `WH/Stock/Zone A/...`, Sortly `All Items > Warehouse 1`).
- **Readable coordinate codes with separate parts.** Use one consistent code shape for each spot (aisle-stack-level style) and store or show its parts separately, so a code can be read from the floor (SAP EWM `01-02-03`).
- **Capacity and mixing rules shown on the location.** Show max weight or count and the mixing policy (empty only / same product / mixed), plus used vs available capacity (Odoo storage categories, SAP bin capacity fields).
- **Empty spots can be filtered.** An "is empty" column or badge and a filter for empty locations on the layout and location table (Odoo **Empty Locations**). The plan view can show empty bins (SAP GWL).
- **Detail pages expose counts as links.** A location or pallet page links to its current stock, products, and rules, each with a count (Odoo smart buttons). A location's inventory tab lists item, quantity, unit, and tracking (Fishbowl).
- **History is one click from any batch, pallet, or location.** Odoo has a **Traceability** button on the lot, **History** on the location row, and **Inventory At Date**.
- **The plan view drills down.** Floor plan → rack/row front view by level → spot pop-up with details and actions, with visible zoom controls (SAP GWL).
- **Mismatch errors state the numbers**, such as "entered 0, expected x", not a generic "invalid" (NetSuite bin error).

### Patterns to avoid

- **Silent over-capacity placement.** Odoo states it does not split quantities and "still routes all items to that same location" when that exceeds capacity. Yongkit should block or warn explicitly. Its existing "Can't save while stock is here" copy points the right way.
- **Layouts that depend on hidden numbering rules.** SAP GWL only groups bins into racks if stacks were generated with even/odd numbering per aisle side. A supervisor should not need a naming convention for the planner to render correctly.
- **ERP-density setup forms.** Fishbowl's location form has 11 location types and five flags. For a supervisor building a layout, show the two or three properties that change behaviour and keep the rest behind "more".

### Patterns to steal

- **The "My day" card puts clock action, today, week, and period in one place.** One clock in/out button, today's entries, and running totals for the week and the pay or attendance period, with a link to the full timesheet (BambooHR widget). The timer state stays synced across phone and desktop (Personio).
- **Missed punches are a guided fix, not a silent gap.** Detect a missing clock-out and offer the two choices: add the end time or start today (Personio). A blocked clock-in opens a screen that explains the options, not just a toast.
- **The leave form shows the consequence before submit.** Show the balance per leave type as of the start date, a warning with the projected value if it would go negative, holidays auto-counted as zero, and a policy reference at the bottom (BambooHR). Allow a certificate photo when the type requires one (Personio).
- **Request status uses one consistent vocabulary.** Every list uses the same status buckets, for example To Review / Approved / Paid / Declined (Gusto). The employee's home shows upcoming absences with their approval status (Personio).
- **The review queue carries a count and a scope switch.** Show a count badge on entry, a "mine vs everyone" toggle, and approve/deny/comment on each item. Deny asks for a note. Overriding earlier approvers needs an explicit confirm (BambooHR **Approve Anyway**).
- **Approvers see context next to the request.** Show who else is out on those days (BambooHR approval email) and the employee's attendance for OT approvals (Prosoft 2.6.2). Approval can happen inline from the home feed (HumanSoft for HR).
- **Who's out today with expected return dates** on the employee home (Personio).
- **Payslips are a dated table with quick ranges.** List pay dates newest first with the current slip one tap away. Bulk download offers Last N / YTD / All / custom, and each slip shows the pay period and leave balances (BambooHR).

### Patterns to avoid

- **A social feed on the worker's home** (HiBob birthdays, "who's celebrating", polls, shoutouts). Factory and warehouse staff open HR to check shift, attendance, or leave. Keep announcements, but not a feed that pushes the clock button below the fold.
- **Irreversible decline with no guard** (Gusto: "Declined requests cannot be undone", so the employee must resubmit). If Yongkit keeps decline final, require a reason and a confirmation step, or allow reopening.
- **US payroll and benefits surfaces** (Gusto and BambooHR tax, direct-deposit, and benefits tabs). Thai payroll has no one-to-one equivalent. Benchmark the layout of the payslip list and detail, not the field set.

### Patterns to steal

- **The default period is named, with its time zone.** Show the default period as "Month to date" (OpenAI) and label the time zone. OpenAI states UTC. Yongkit should state Asia/Bangkok or UTC, because the day boundaries differ by 7 hours.
- **Cost and activity are separate views.** Spend in money and activity in counts or tokens are distinct tabs or sections and distinct exports (OpenAI Cost/Activity data, Anthropic Usage/Cost pages). Yongkit maps this to actual USD vs estimated THB vs scan counts.
- **Every dimension filter has an explicit "All".** Use the same filter row everywhere (workspace/project, model, key, and for Yongkit warehouse, user, feature), each with an "All" option (Anthropic). Group-by covers project, user, key, and model (OpenAI).
- **Charts drill down.** Clicking a bar narrows to a finer time grain (Anthropic hour/minute).
- **The in-progress period is marked and projected.** Toggle or label the partial current period, with a projection (Clerk **Show incomplete period**, Vercel projected cost per item).
- **A freshness line saying how current the data is**, for example "complete through end of previous day" (Clerk).
- **Unknown is labelled, never shown as zero.** Untracked or unattributed spend gets its own label (OpenAI "Untracked"). Totals state what they include, for example token vs tool cost (Anthropic).
- **Alert thresholds are visible next to spend**: a default alert at 100% of the budget, more thresholds can be added, and soft vs hard limits are clearly distinguished (OpenAI, Vercel Spend Management).

### Patterns to avoid

- **One metric table per product area** (Vercel has more than ten resource sections). Yongkit has three features to report: job-ticket scan, location-label scan, and AI Search. Use one breakdown with a feature dimension.
- **No per-user breakdown** (Anthropic: "not possible to break down usage or cost by individual users"). Yongkit's product rule is per-actor attribution. Do not copy this gap.
- **UTC-only timestamps with no visible label for a Bangkok organization.** OpenAI states UTC only in help docs. Yongkit must label the zone on screen.

### Patterns to steal

- **Useful before the first keystroke.** On open, show recent pages or items with timestamps, and favourites or shortcuts (Notion, Linear, Raycast, GitHub "resources you've used recently").
- **A visible scope chip.** Show the current section (for example People or Warehouse) as a removable chip that scopes results (GitHub top-left scope, Backspace to widen).
- **Exact codes jump.** Typing a job-ticket number, pallet code, or employee ID opens that record directly, tolerating missing separators (Linear `LIN-123` and `lin123`).
- **Matches are highlighted** in result titles (Linear).
- **AI is an explicit, labelled row below the box.** "Search with AI" opens a results view whose answer cites the pages it used (Notion **Search all sources with AI**, "with citations").
- **No results still offers a next step.** Offer fallback actions that reuse the query, for example "Ask AI about '…'" or "Search employees for '…'" (Raycast fallback commands).
- **Keyboard contract.** Arrows plus Enter, Ctrl/Cmd+Enter for a new tab, and Esc clears then closes (GitHub, Raycast). The placeholder says what can be searched (Raycast).
- **Results are grouped and ranked by use.** Group results by type and rank by recent and frequent use for the same query (Raycast frecency, Linear status ordering).

### Patterns to avoid

- **Prefix-character modes as the only way to filter** (GitHub `>`, `#`, `@`, `/`, `!`). HR and warehouse users won't discover them. If Yongkit adds modes, expose them as visible chips. Prefixes can be an extra.
- **Separate entry points for search and commands** (Linear `/` vs Cmd/Ctrl+K). Yongkit should keep one trigger and one dialog.
- **Developer-only affordances in the main path**, such as copy-URL shortcuts and deep links (GitHub Ctrl+C, Raycast deeplinks). They are fine as hidden extras but should not add rows to results.

## Audit rubric anchors

Each line can be checked from a screenshot or the DOM. Tags name the product or products the anchor comes from. Score down only for anchors that fit the screen's purpose.

### 1. Warehouse mobile scanning

- Each scanned line or ticket shows a scanned/expected count (`n/N`) or an explicit done state, and done uses icon or text as well as colour. _(Odoo)_
- A single instruction line says what to scan next, and the camera view shows a live state prompt (aim / hold still / move closer / processing). _(Odoo, ML Kit showcase)_
- The scan screen accepts the next code without the user first tapping a field, and job tickets and location labels are routed automatically. _(Katana)_
- An unrecognised or wrong code shows the code value plus at least one action (rescan, enter manually, link or create). It does not just dismiss. _(Odoo, Katana)_
- Manual entry is reachable from the scan screen. If the camera is unavailable, the screen explains why below the input. _(SAP Fiori)_
- A location scan that doesn't match the expected destination is blocked or flagged, and changing the destination is a separate labelled action. _(SAP EWM RF)_
- Quantity changes work without the soft keyboard (stepper, number pad, or fill-to-expected). _(Odoo)_
- The primary scan control is the visually dominant action on the screen and is at least 48 CSS px tall. _(SAP Fiori, Material)_

### 2. Warehouse desktop

- Every location reference shows its full path (building › floor › zone › spot), including in tables and search results. _(Odoo, Sortly)_
- Spot codes follow one consistent, readable pattern, and their parts are visible or filterable. _(SAP EWM)_
- The location or spot detail shows used vs available capacity and the mixing rule. _(Odoo storage categories, SAP bin fields)_
- Empty spots can be identified at a glance (badge, column, or filter). _(Odoo, SAP GWL)_
- Pallet, batch, and location detail pages link to their history in one click. _(Odoo Traceability/History)_
- The layout view has visible zoom controls, and clicking a spot opens its details without leaving the plan. _(SAP GWL)_
- Validation errors state the conflicting numbers or the reason (for example "stock is here", "expected 3, got 0"). _(NetSuite, Odoo)_

### 3. People / HR

- "My day" shows the clock action, today's entries, and the week and period totals without scrolling on a 390 px-wide viewport. _(BambooHR, Personio)_
- A missing clock-out or a blocked clock-in leads to a screen that offers explicit fix options. _(Personio)_
- The leave form shows the balance for the selected type as of the start date before submit, and warns with the projected value if it would go negative. _(BambooHR)_
- Request lists use one status vocabulary with consistent badge colours and text on every HR screen. _(Gusto, Personio)_
- The review queue shows a pending count and a scope switch (mine/all), and each item can be approved or denied from the queue. _(BambooHR)_
- Deny or decline requires or offers a reason, and an irreversible action has a confirmation step. _(BambooHR, Gusto)_
- Approvers see context next to the request: overlapping absences and attendance for the dates. _(BambooHR, Prosoft myHR Cloud)_
- Payslips list pay dates newest first, with the pay period visible on each row or on the detail. _(BambooHR)_

### 4. Administration: AI usage

- The period control defaults to this month and names it, and the time zone is visible on the page. _(OpenAI, Clerk)_
- Money and activity are visually separate, and USD actual vs THB estimate are labelled distinctly. _(OpenAI, Anthropic; PRODUCT.md)_
- Each filter (feature, warehouse, user, model) offers an explicit "All". _(Anthropic)_
- Unknown cost is shown with its own label or style, never as `0` or `$0.00`. _(OpenAI "Untracked"; PRODUCT.md)_
- The current partial period is marked as incomplete or projected. _(Clerk, Vercel)_
- A data-freshness or "last updated" line is present. _(Clerk)_
- CSV export is reachable from the report and exports the filtered view. _(Anthropic, OpenAI)_

### 5. Global search and AI search

- Opening search with an empty query shows recent items or shortcuts, not a blank panel. _(Notion, Linear, Raycast, GitHub)_
- The current scope or section is visible in the dialog and can be removed. _(GitHub)_
- Typing an exact record code (ticket, pallet, employee ID) puts that record first. _(Linear)_
- Query matches are highlighted in result titles. _(Linear)_
- AI Search is a labelled row or button, not mixed in with keyword results, and AI answers show their source pages. _(Notion)_
- A zero-result query offers at least one fallback action that reuses the query. _(Raycast)_
- Keyboard: arrows move the selection, Enter opens, Esc clears then closes, and focus returns to the trigger on close. _(GitHub, Raycast)_

### Cross-cutting anchors

- **Thai line height.** Material classes Thai as a "tall" script that needs extra line height. Check that tone marks and above/below vowels (ั ิ ี ่ ้ ุ ู) are not clipped in buttons, badges, table cells, inputs, and single-line truncations, and that no container has a fixed height that cuts them. _(Material [language support](https://m2.material.io/design/typography/language-support.html) [S])_
- **Thai wrapping.** Thai has no spaces between words and should wrap "a word at a time" ([W3C line breaking](https://w3c.github.io/i18n-drafts/articles/typography/linebreak.en) [V]). Check for mid-word breaks in narrow columns and chips, and for ๆ starting a line. The W3C reports that all three engines fail that case ([Thai gap analysis](https://www.w3.org/TR/thai-gap/) [S]).
- **Mixed-language strings.** Thai labels next to Latin codes (job numbers, pallet codes) share a baseline and don't overflow at Thai lengths. Check both `th` and `en` locales on the same screen. _(Yongkit-internal; no external source)_
- **Touch targets.** At least 24×24 CSS px everywhere ([WCAG 2.2 SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) [V]). At least 48×48 for scan, clock, approve, and other primary mobile actions, with about 8 px between targets ([Material accessibility](https://m3.material.io/foundations/designing/structure) [S]).
- **Dark and light mode.** Status colours (done, warning, error, unknown) stay distinguishable in both modes and never rely on colour alone. _(Yongkit-internal; no external benchmark verified in this pass)_
- **Empty states.** Explain what the area is for, with only one primary call to action and no guilt-laden copy ([Polaris empty state](https://polaris-react.shopify.com/components/layout-and-structure/empty-state) [A]). Empty is distinct from "filtered to nothing" and from "unknown".
- **Loading states.** Long work names what is happening ("Searching…", "processing"), as in the ML Kit showcase prompts. Preserve the layout while loading rather than swapping in a blank screen.
- **Error states.** Say why and what to do next, close to the failed control. SAP Fiori puts the reason under the input ("Scanner not available"), and NetSuite states the numbers. Drafts survive a failed save (Yongkit copy: "Not saved. Your changes are still here.").
